Fragment Shader Interlock and Raster Order in OpenGL

Fragment shader interlock is an OpenGL synchronization mechanism that provides hardware-level guarantees for serialized execution of overlapping fragments in primitive submission order. This article explains how fragment shader interlock functions, how it maps to the Rasterizer Ordered View (ROV) concept found in other graphics APIs, and how developers can utilize it in OpenGL to safely perform programmable blending and avoid data races without relying on complex multi-pass algorithms.

The Concurrency Problem in Fragment Shading

Modern GPUs execute thousands of fragment shader invocations concurrently. When multiple primitives overlap the same screen coordinates, their respective fragment shaders run in an undefined order unless passed through the fixed-function blending pipeline.

If a developer attempts programmable blending, custom framebuffers, or structures like Order-Independent Transparency (OIT) via Shader Storage Buffer Objects (SSBOs) or image load/store operations, standard parallel execution creates data races. Standard atomic operations solve race conditions for basic math, but they do not enforce sequential execution or preserve primitive rasterization order.

What is Fragment Shader Interlock?

Fragment shader interlock, introduced via extensions such as GL_ARB_fragment_shader_interlock (as well as vendor-specific extensions from Intel and NVIDIA), allows developers to designate a critical section within a fragment shader.

When an invocation reaches this critical section, the GPU guarantees that no other fragment shader invocation covering the same pixel or sample can execute that critical section concurrently. Furthermore, when ordered interlock is specified, the hardware guarantees that overlapping invocations enter the critical section strictly in API primitive submission order.

How It Delivers Raster Order View (ROV) Guarantees

In DirectX 11.3 and 12, the hardware capability that serializes access to unordered access views (UAVs) based on rasterization order is known as Rasterizer Ordered Views (ROVs).

OpenGL’s fragment shader interlock provides the exact same guarantee using GLSL layout qualifiers and synchronization intrinsics:

  1. Ordering Modes: OpenGL allows developers to declare the granularity and ordering rules of the critical section at the top of the shader:

    • layout(pixel_interlock_ordered) in; enforces that fragments covering the same \((x, y)\) screen pixel execute in primitive submission order.
    • layout(sample_interlock_ordered) in; enforces serialization per multisample anti-aliasing (MSAA) sample rather than per pixel.
    • Unordered variants (pixel_interlock_unordered) enforce mutual exclusion without enforcing rasterization order, similar to a mutex.

  2. Demarcating the Critical Section: Inside main(), the code enters and exits the serialized zone using two intrinsic functions:

    beginInvocationInterlockARB();

// Critical section: safely read, modify, and write memory
vec4 current = imageLoad(customTarget, coords);
vec4 blended = customBlend(current, incomingColor);
imageStore(customTarget, coords, blended);

endInvocationInterlockARB();

  3. Memory Synchronization: Inside the interlock boundary, memory accesses to images or SSBOs behave deterministically. Memory written by a previously submitted primitive at the same pixel location is guaranteed to be visible to the subsequent primitive entering the interlock block.

Practical Applications

By providing ROV semantics directly inside GLSL, fragment shader interlock eliminates the need for sorting stages or multi-pass rendering in several advanced techniques:

  • Single-Pass Order-Independent Transparency (OIT): Fragment fragments can be inserted into per-pixel linked lists or blended into a single buffer deterministically without depth-sorting overhead.
  • Custom Programmable Blending: Enables mathematical blend modes that are unsupported by the fixed-function blending hardware (such as non-separable blend modes or HDR tone mapping directly in the blend stage).
  • Software Depth and Stencil Emulation: Allows developers to implement custom early-Z or complex stencil testing directly within storage buffers.

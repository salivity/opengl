GPU-Driven Rendering with glDrawElementsIndirect

Indirect rendering via glDrawElementsIndirect shifts draw call parameter generation from the CPU to the GPU by reading execution commands directly from buffer storage. Instead of the CPU specifying how many elements or instances to render at the moment of dispatch, it points the GPU to a buffer containing those parameters. This architecture enables the GPU to evaluate visibility, alter geometry metrics, and dispatch rendering commands dynamically without CPU intervention or costly synchronization stalls.

The Traditional CPU Bottleneck

In conventional OpenGL rendering, functions like glDrawElements or glDrawElementsInstanced require the CPU to supply draw parameters explicitly. The CPU must specify the number of indices, instance counts, and base offsets as function arguments.

If a scene requires dynamic culling (such as frustum or occlusion culling) or level-of-detail (LOD) selection, the CPU must compute which objects are visible. If this calculation is offloaded to a compute shader, the CPU typically must read the visibility results back from the GPU to determine the final draw arguments. This readback creates a pipeline stall, forcing the CPU to wait for the GPU to finish its work, which severely degrades performance.

The Mechanism of glDrawElementsIndirect

glDrawElementsIndirect bypasses this limitation by decoupling draw command issuance from draw parameter definition. The function signature takes an indirect draw command from a buffer bound to the GL_DRAW_INDIRECT_BUFFER target:

void glDrawElementsIndirect(GLenum mode, GLenum type, const void *indirect);

The indirect parameter is not a pointer to client memory; it is a byte offset into the currently bound GL_DRAW_INDIRECT_BUFFER. The GPU reads a specific structure directly from this buffer:

typedef struct {
    GLuint count;
    GLuint instanceCount;
    GLuint firstIndex;
    GLint  baseVertex;
    GLuint baseInstance;
} DrawElementsIndirectCommand;

Because these parameters reside inside a standard OpenGL buffer object, the data can be created, updated, and manipulated natively on the GPU without CPU involvement.

How the GPU Drives Its Own Execution

The key to GPU-driven rendering lies in combining indirect draw buffers with compute shaders:

  1. Parameter Generation: A compute shader executes before the rasterization phase, evaluating scene geometry. Each compute thread can represent an object, bounding volume, or meshlet.
  2. Culling and LOD Selection: The compute shader performs frustum checks, hi-Z occlusion queries, and distance calculations entirely within GPU memory.
  3. Buffer Writes: When an object passes visibility tests, the compute shader uses atomic operations or direct writes to populate the DrawElementsIndirectCommand structure in the bound buffer. If an object is completely culled, the compute shader simply sets instanceCount or count to 0.
  4. Execution: The CPU issues glDrawElementsIndirect (or its batch equivalent, glMultiDrawElementsIndirect). The GPU reads the buffer it just populated and processes the geometry immediately.

Pipeline Efficiency and Synchronization Benefits

By sourcing draw parameters from GPU memory, indirect rendering eliminates round-trip latency. The CPU no longer needs to wait for culling results, allowing it to submit render calls freely while remaining asynchronously ahead of the GPU.

Furthermore, when used alongside glMultiDrawElementsIndirect, a single API call can execute thousands of separate mesh draws with varying instance counts and offsets. This consolidation minimizes OpenGL driver overhead, reduces CPU instruction cycles, and ensures the graphics pipeline remains saturated purely through GPU-managed data flow.

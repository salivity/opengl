How to Build a Spin-Lock in OpenGL Compute Shaders

This article details how to implement a functional spin-lock synchronization primitive inside an OpenGL compute shader using OpenGL Shading Language (GLSL). It covers the required memory qualifiers, atomic operations for acquiring and releasing locks, the role of memory barriers, and the critical hardware architecture limitations—such as SIMT execution and scheduling deadlocks—that developers must navigate to avoid device timeouts.

Understanding the GPU Memory Model

To create a cross-invocation lock on the GPU, data must be globally visible across different execution units. Standard local variables or default Shader Storage Buffer Objects (SSBOs) may cache values in registers or L1 caches without propagating modifications immediately.

To bypass this caching and ensure that changes are immediately visible to all compute units, the lock variable must be defined within an SSBO using the coherent memory qualifier.

#version 450 core

layout(std430, binding = 0) coherent buffer MutexBuffer {
    uint lockState; // 0 = unlocked, 1 = locked
};

The coherent keyword tells the compiler and memory subsystem that writes to lockState must be made visible to other shader invocations accessing the same buffer.

Implementing the Lock Acquisition

Spinning requires an atomic Compare-And-Swap (CAS) operation. In GLSL, this is provided by atomicCompSwap(mem, compare, data).

The function compares the current value stored in mem with compare. If they match, it replaces the value with data. In either case, it returns the value that was stored in mem immediately before the operation.

void acquireLock() {
    // Loop until atomicCompSwap successfully replaces 0 (unlocked) with 1 (locked)
    while (atomicCompSwap(lockState, 0u, 1u) != 0u) {
        // Spin wait
    }
    
    // Ensure all subsequent memory reads/writes happen after the lock is acquired
    memoryBarrierBuffer();
}

The memoryBarrierBuffer() call directly after the loop is mandatory. It ensures ordering: no memory accesses inside the protected critical section can be reordered by the compiler or the memory controller prior to the point where the lock was secured.

Implementing the Lock Release

Releasing the lock involves writing 0u back to lockState. To prevent race conditions and memory reordering, a barrier must precede the release, followed by an atomic write.

void releaseLock() {
    // Flush all pending writes to the buffer before releasing the lock
    memoryBarrierBuffer();
    
    // Atomically reset the lock state to 0
    atomicExchange(lockState, 0u);
}

Using atomicExchange(lockState, 0u) guarantees an atomic store that flushes immediately to the memory hierarchy, alerting other spinning invocations that the resource is free.

Full Example Compute Shader

#version 450 core

layout(local_size_x = 64, local_size_y = 1, local_size_z = 1) in;

layout(std430, binding = 0) coherent buffer SyncBuffer {
    uint lockState;
    uint sharedCounter;
};

void acquireLock() {
    while (atomicCompSwap(lockState, 0u, 1u) != 0u) {
    }
    memoryBarrierBuffer();
}

void releaseLock() {
    memoryBarrierBuffer();
    atomicExchange(lockState, 0u);
}

void main() {
    acquireLock();

    // Critical Section
    sharedCounter += 1u;

    releaseLock();
}

Hardware Traps and Deadlock Hazards

While this pattern is syntactically correct, deploying spin-locks on GPUs comes with severe architectural risks that do not exist on CPUs:

  1. Warp/Wavefront Divergence (Lockstep Deadlock): Threads within the same 32-thread (NVIDIA) or 64-thread (AMD) subgroup execute instructions in lockstep (SIMT). If Thread 0 acquires the lock and enters the critical section, while Thread 1 in the same subgroup fails and enters the while spin loop, Thread 0 may never be scheduled to reach releaseLock(). The entire warp deadlocks immediately. Rule: Never use a spin-lock between threads in the same subgroup. Elect a single thread per subgroup using subgroup operations, or synchronize only across separate workgroups.

  2. Workgroup Scheduling and Starvation: GPUs execute a limited number of workgroups concurrently based on available Compute Units (CUs) or Streaming Multiprocessors (SMs). If an active workgroup spins waiting for a lock held by a workgroup that has not yet been scheduled by the hardware dispatcher, the active workgroup will spin infinitely. This triggers the OS-level Timeout Detection and Recovery (TDR), causing the driver or GPU to crash.

  3. Performance Overhead: Spin-locks saturate memory buses with atomic requests, degrading performance across all running shaders. Whenever possible, replace spin-locks with atomic counters, parallel reductions, or multi-pass dispatch strategies.

OpenGL Driver Interaction with BC1 to BC7 Textures

This article explains how desktop OpenGL drivers ingest, manage, and dispatch block-compressed textures ranging from BC1 through BC7. It covers the translation between DirectX block compression standards and OpenGL internal formats, the mechanism of texture upload via driver APIs, how desktop GPU texture mapping units natively unpack block data at runtime, and key driver-level considerations such as sRGB conversions and sub-4x4 pixel mipmap handling.

Format Mapping and Extension Exposure

Block Compression (BC) formats originated primarily within Microsoft's Direct3D ecosystem, but desktop OpenGL drivers expose native support for them through specific OpenGL core specifications and Architecture Review Board (ARB) or vendor extensions. Because modern desktop graphics hardware features unified silicon for Direct3D and OpenGL, drivers provide a one-to-one mapping between BC formats and internal OpenGL enumerants:

  • BC1, BC2, BC3: Exposed originally via GL_EXT_texture_compression_s3tc and modern core profiles. BC1 maps to GL_COMPRESSED_RGB_S3TC_DXT1_EXT or GL_COMPRESSED_RGBA_S3TC_DXT1_EXT (8 bytes per 4x4 block). BC2 maps to GL_COMPRESSED_RGBA_S3TC_DXT3_EXT (16 bytes per 4x4 block). BC3 maps to GL_COMPRESSED_RGBA_S3TC_DXT5_EXT (16 bytes per 4x4 block).
  • BC4, BC5: Exposed via GL_ARB_texture_compression_rgtc (promoted to OpenGL 3.0 core). BC4 maps to GL_COMPRESSED_RED_RGTC1 (signed/unsigned, 8 bytes per block), and BC5 maps to GL_COMPRESSED_RG_RGTC2 (signed/unsigned, 16 bytes per block).
  • BC6H, BC7: Exposed via GL_ARB_texture_compression_bptc (promoted to OpenGL 4.2 core). BC6H maps to GL_COMPRESSED_RGB_BPTC_SIGNED_FLOAT_ARB and GL_COMPRESSED_RGB_BPTC_UNSIGNED_FLOAT_ARB. BC7 maps to GL_COMPRESSED_RGBA_BPTC_UNORM_ARB and its sRGB counterpart (all 16 bytes per block).

Desktop drivers query the GPU's hardware capabilities at context creation and populate the extension strings and format query tables (glGetInternalformativ) to declare support for these formats.

Ingestion and Memory Allocation

Applications provide pre-compressed data directly to the driver using functions such as glCompressedTexImage2D or glCompressedTexSubImage2D. During this call, the driver performs minimal CPU overhead:

  1. Validation: The driver verifies that the byte size passed by the host matches the expected calculation: ceil(width / 4) * ceil(height / 4) * blockSize.
  2. Memory Layout Allocation: The driver requests a virtual memory allocation from the GPU kernel driver. Rather than storing textures linearly, desktop drivers (such as those from NVIDIA, AMD, and Intel) arrange memory into proprietary tiled or swizzled micro-tile patterns (e.g., Morton order or recursive Z-order curves) to optimize cache locality during rendering.
  3. DMA Transfer: The compressed payload is copied into a staging buffer or directly queued via direct memory access (DMA) into VRAM without software decompression.

If an application passes an uncompressed format (such as GL_RGBA8) and specifies a compressed internal format like GL_COMPRESSED_RGBA_BPTC_UNORM, the driver is technically allowed to perform real-time software or compute-based compression. However, desktop drivers universally implement slow fallback paths for real-time driver compression, making runtime compression in production environments impractical.

Hardware Sampling and Silicon Decompression

At no point does the OpenGL driver decompress BC1–BC7 textures into full-resolution RGBA data in system RAM or VRAM. Instead, textures remain compressed in VRAM and through the L2 cache.

When a shader invokes a texture sampling function (e.g., texture() in GLSL):

  1. The Texture Mapping Unit (TMU) fetches the required 4x4 block(s) from memory or the L1 texture cache.
  2. Dedicated, fixed-function hardware decoders integrated into the TMU unpack the compressed endpoints, palette indices, and partition sets on the fly.
  3. The decoded texels are interpolated (using bilinear, trilinear, or anisotropic filtering) directly inside the hardware pipeline.
  4. The final filtered value is returned to the shader register as an uncompressed 32-bit float vector.

Because decompression occurs transparently inside the silicon, the driver's role during draw execution is limited to setting the correct hardware state registers that inform the TMU of the texture's internal encoding scheme, color space, and memory strides.

sRGB Handling

For formats supporting sRGB data (such as BC1, BC2, BC3, and BC7), the driver provides distinct internal format tokens (e.g., GL_COMPRESSED_SRGB_ALPHA_BPTC_ARB).

When these formats are bound, the driver programs the hardware TMU to perform linear color conversion in a specific sequence: the 4x4 block is first decompressed into discrete 8-bit non-linear values, then converted into linear floating-point space via hardware look-up or math logic, and finally filtered. This ensures filtering calculations avoid gamma-induced edge darkening artifacts without requiring CPU intervention or shader overhead.

Sub-4x4 Mipmap Handling

Block compression formats operate exclusively on 4x4 pixel matrices. For mipmapped textures where lower levels drop below 4x4 dimensions (e.g., \(2 \times 2\), \(1 \times 1\)), the driver enforces the minimum payload allocation of one full block:

  • A \(2 \times 2\) or \(1 \times 1\) mip level still consumes a full 8-byte (BC1, BC4) or 16-byte (BC2, BC3, BC5, BC6H, BC7) payload.
  • The driver configures the GPU's addressing registers to treat the unused pixels within that terminal block as padding, sampling only the valid top-left sub-region to prevent bleeding artifacts.

How OpenGL texelFetch Reads Raw Texel Data

In modern OpenGL, texelFetch allows shaders to retrieve exact, unadulterated texel values directly from a texture without the overhead or modification of standard texture sampling pipelines. Unlike standard texture sampling functions such as texture(), which use normalized floating-point coordinates and route through dedicated interpolation units, texelFetch operates using integer coordinates and explicit level-of-detail indices. This article explains the underlying mechanics of how texelFetch bypasses the GPU's Texture Filtering Units (TFUs), circumvents sampler state parameters, and executes as an indexed memory load directly from the texture cache.

The Conventional Texture Sampling Pipeline

To understand how texelFetch circumvents hardware filtering, it is essential to examine the standard texture sampling path. When a shader calls texture(sampler2D, vec2):

  1. Coordinate Normalization and Wrapping: The hardware receives normalized coordinates (ranging from 0.0 to 1.0), scales them by the texture dimensions, and applies wrap modes defined in the sampler state (such as GL_REPEAT, GL_CLAMP_TO_EDGE, or GL_MIRRORED_REPEAT).
  2. LOD and Derivative Computation: The GPU computes partial derivatives (\(\frac{\partial u}{\partial x}\), \(\frac{\partial v}{\partial y}\)) across adjacent fragments in a \(2\times2\) quad to select the appropriate mipmap level.
  3. Hardware Filtering: The coordinates are routed into dedicated silicon known as Texture Filtering Units (TFUs). Depending on the sampler configuration (GL_LINEAR, GL_LINEAR_MIPMAP_LINEAR), the TFU fetches the surrounding four or eight texels and computes a weighted average via hardware interpolation before returning a color to the shader register.

How texelFetch Alters the Data Path

texelFetch diverges completely from this execution path by eliminating normalized coordinate math, derivative generation, and interpolation logic.

1. Integer-Based Addressing

Instead of normalized floating-point coordinates, texelFetch takes integer vectors (ivec2 for 2D textures, ivec3 for 3D textures) representing the discrete grid coordinates of a specific texel (\([0, \text{width}-1]\), \([0, \text{height}-1]\)). This replaces fractional coordinate evaluation with direct array indexing. Because there are no fractional components, the concept of a sub-pixel location does not exist, removing any mathematical basis for bilinear or bicubic filtering.

2. Manual Mipmap and Layer Indexing

Standard sampling relies on quad-derivatives to dynamically determine mipmap levels. texelFetch requires the level-of-detail (LOD) to be explicitly provided as an integer argument (or an integer sample index for multisampled textures). Because the mip level is predetermined at the call site, the GPU skips the entire automatic LOD calculation phase.

3. Bypassing Sampler State and TFUs

Samplers bind filtering settings (GL_TEXTURE_MIN_FILTER, GL_TEXTURE_MAG_FILTER) and wrapping rules to textures. When a shader invokes texelFetch, these sampler states are ignored:

  • No Wrap Modes: If the supplied integer coordinates fall outside the boundaries of the specified mip level, the behavior is undefined or returns zeroes depending on the architecture and bounds-checking extensions. The hardware does not evaluate clamping or wrapping logic.
  • TFU Bypass: Because no blending across texels or mip levels is required, the request bypasses the Texture Filtering Unit entirely. The instruction is handled similarly to an explicit memory load or a buffer fetch (imageLoad), translating the coordinate directly into an absolute linear memory offset.

Architectural Execution

At the GPU ISA (Instruction Set Architecture) level, standard texture operations compile to specialized texture sampling instructions (such as TEX on various architectures), which queue data through the texture pipeline's decompression and filtering stages.

In contrast, texelFetch often compiles down to direct texture load instructions (such as TLD or TEX.B on NVIDIA architectures, or IMAGE_LOAD on AMD GCN/RDNA). The GPU's address generation unit computes the memory address using the formula:

\[\text{Address} = \text{Base} + (\text{MipOffset}) + (y \times \text{RowPitch}) + (x \times \text{BytesPerTexel})\]

The GPU checks the L1/L2 texture caches for the computed address. If the data is present, the raw, uncompressed bits are converted directly to the format of the target vector (e.g., float, integer, unsigned integer) and loaded into the destination registers.

Common Use Cases

By bypassing filtering hardware, texelFetch delivers deterministic, bit-exact access to texels at lower latency than filtered fetches. This makes it the primary tool for:

  • G-Buffer Access: Reading depth, normal, and material ID textures in deferred rendering passes where color blending would introduce invalid intermediate values.
  • Data Textures: Storing non-color data such as transformation matrices, lookup tables, or discrete state flags.
  • Multisample Textures: Resolving or inspecting individual samples within a multisampled render target (sampler2DMS).

SoA vs AoS OpenGL Performance Comparison

Choosing between Structure-of-Arrays (SoA) and Array-of-Structures (AoS) memory layouts in OpenGL fundamentally dictates how data travels from system memory to the GPU core. This article compares how both layouts interact with GPU cache lines, vertex fetch hardware, and compute shaders, explaining the performance trade-offs of each approach in modern graphics pipelines.

Understanding the Layouts in OpenGL

In an Array-of-Structures (AoS) format, all attributes for a single element are grouped together contiguously. In standard OpenGL vertex buffer objects (VBOs), this is known as interleaved vertex data:

[Pos, Normal, UV], [Pos, Normal, UV], [Pos, Normal, UV]

In a Structure-of-Arrays (SoA) format, each attribute is stored in its own contiguous array across all elements. In OpenGL, this translates to either using multiple separate VBOs or binding distinct offsets within a single large buffer:

[Pos, Pos, Pos], [Normal, Normal, Normal], [UV, UV, UV]

Vertex Shader Performance and Attribute Fetching

For standard geometry rendering where a vertex shader consumes every declared attribute (e.g., position, normal, tangent, and texture coordinates), AoS generally outperforms SoA.

When the GPU vertex fetch stage loads data, it reads from memory in fixed cache-line chunks (typically 32 to 128 bytes). With AoS, pulling one vertex pulls all of its associated attributes into the cache simultaneously. This maximizes spatial locality and keeps the GPU memory controller’s active read streams to a minimum.

Using pure SoA during a full-attribute draw call forces the memory controller to manage multiple concurrent memory streams—one for each bound attribute buffer. This can saturate cache lines with future data that might be evicted before it is consumed, leading to cache thrashing and increased memory latency.

The Depth-Prepass and Shadow Pass Exception

The dynamic changes dramatically when shaders only read a subset of the available vertex attributes, such as in depth pre-passes, shadow map generation, or physics collision detection.

In an AoS layout, if the GPU only needs vertex positions, it still fetches the entire interleaved struct into the cache. The normals, tangents, and UVs are loaded across the bus and immediately discarded, wasting up to 70–80% of available memory bandwidth.

In an SoA layout, the depth pass binds only the position array. Memory bandwidth utilization approaches 100%, and cache lines contain purely relevant data. In bandwidth-constrained scenes with heavy shadow mapping, switching positions to an isolated array yields substantial performance improvements.

Compute Shaders and Memory Coalescing

In OpenGL Compute Shaders (using Shader Storage Buffer Objects or SSBOs), the preference decisively shifts toward SoA.

GPUs execute compute threads in warps (NVIDIA, 32 threads) or wavefronts (AMD, 64 threads) using SIMD (Single Instruction, Multiple Data) architecture. Memory transactions are most efficient when threads in a warp access consecutive memory addresses simultaneously—a mechanism called memory coalescing.

  • SoA: Thread 0 accesses index 0, Thread 1 accesses index 1, and so forth. The memory controller merges these accesses into a single continuous transaction.
  • AoS: Thread 0 accesses index 0 (bytes 0–31), Thread 1 accesses index 1 (bytes 32–63), creating large strides between reads. The hardware must issue multiple memory transactions to fulfill the request, degrading throughput unless the entire structure size perfectly aligns with vector data types like vec4.

Dynamic Buffer Updates

SoA offers distinct performance benefits when vertex data is updated dynamically from the CPU or a transform feedback/compute pass:

  • Updating a single attribute (such as animated texture coordinates or blend shapes) in AoS requires either mapping the entire buffer and striding writes—which ruins CPU cache efficiency—or updating unneeded static data alongside dynamic data.
  • With SoA, only the target attribute buffer needs to be mapped, uploaded, or orphaned via glBufferSubData, minimizing CPU-to-GPU transfer sizes.

Recommended Hybrid Strategy

Rather than adopting a pure AoS or pure SoA pipeline, modern OpenGL architectures benefit most from a hybrid layout:

  1. Positions as a dedicated stream (SoA style): Keep vec3 position data in its own separate buffer or contiguous offset to optimize depth passes, shadow passes, and early-Z culling.
  2. Interleaved secondary attributes (AoS style): Group normals, tangents, UVs, and colors into an interleaved array, as these are virtually always consumed together during main shading passes.
  3. SSBOs in Compute Shaders: Store persistent compute data in SoA layout to ensure uniform memory coalescing across all hardware threads.

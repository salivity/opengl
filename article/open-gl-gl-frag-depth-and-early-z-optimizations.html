OpenGL gl_FragDepth and Early-Z Optimizations

Writing arbitrary values to the gl_FragDepth built-in variable in an OpenGL fragment shader overrides the hardware-generated window space depth value for a fragment. While this grants programmatic control over depth testing, it fundamentally breaks several fixed-function hardware optimizations designed to discard occluded fragments before shading occurs. This article details the specific performance mechanisms compromised by modifying gl_FragDepth and outlines how modern OpenGL features can mitigate the resulting pipeline stalls.

1. Early Fragment Tests (Early-Z)

Under standard rendering conditions, modern GPUs run depth and stencil tests before executing the fragment shader—a feature known as Early-Z. If an incoming fragment fails the depth test, the GPU discards it immediately, avoiding the computational cost of running complex lighting, texturing, or procedural logic.

When a shader writes to gl_FragDepth, the final depth value is indeterminate until the fragment shader finishes executing. Consequently, the GPU is forced to defer the depth test until the end of the pipeline (Late-Z). Every fragment generated by rasterization must execute its fragment shader in full, even if it is completely occluded by previously rendered geometry. In scenes with significant overdraw, this can drastically reduce the frame rate due to wasted arithmetic and texture operations.

2. Hierarchical Z (Hi-Z) and Coarse Depth Rejection

GPUs utilize coarse, low-resolution depth representations often referred to as Hierarchical Z (Hi-Z) or Z-Cull. Instead of testing individual pixels, the rasterizer evaluates entire tiles or quads of pixels against a bounding depth range:

  • Tile-Level Rejection: If the minimum depth of a triangle tile is farther than the maximum depth recorded in the Hi-Z buffer for that tile, the entire group of fragments is rejected at once.
  • Impact of Arbitrary Depth: Because an arbitrary write to gl_FragDepth can assign any value—potentially moving a fragment from behind existing geometry to in front of it—the hardware cannot safely reject tiles using the precomputed depth data. As a result, Hi-Z testing is either disabled entirely or limited to non-updating reads, flooding the pipeline with fragments that would otherwise have been discarded as a group.

3. Depth Buffer Compression and Fast Clears

Modern graphics cards employ lossless compression algorithms on depth buffers to conserve memory bandwidth. These systems often depend on predictable, monotonically increasing or decreasing depth values produced by standard rasterization algorithms.

Writing arbitrary values to gl_FragDepth introduces localized discontinuities in the depth surface. This can:

  • Prevent the memory controller from compressing depth blocks effectively.
  • Force decompression of existing depth tiles to perform read-modify-write cycles at full precision.
  • Invalidate fast-clear metadata, leading to increased memory bus saturation when reading and writing to the depth-stencil attachment.

4. Hidden Surface Removal in Mobile Architectures (TBDR)

On mobile and embedded GPUs utilizing Tile-Based Deferred Rendering (TBDR)—such as Imagination PowerVR, ARM Mali, or Qualcomm Adreno—arbitrary depth writes are particularly costly.

TBDR architectures store tile depth buffers in ultra-fast, on-chip SRAM and use features like Hidden Surface Removal (HSR) or Forward Pixel Kill (FPK) to defer shading until primitive visibility is fully resolved. Writing to gl_FragDepth prevents the tile processor from knowing visibility up front, breaking the deferred shading model and causing the GPU to fall back to less efficient immediate-style rendering passes that consume significant memory bandwidth and battery power.

Mitigating the Penalty: Conservative Depth Qualifiers

To recover hardware optimization capabilities when modifying depth, OpenGL 4.2 introduced conservative depth layout qualifiers (originally via the GL_ARB_conservative_depth extension).

If a shader does not write completely arbitrary values, developers can declare constraints on how gl_FragDepth behaves relative to the fixed-function depth (gl_FragCoord.z):

  • layout (depth_greater) out float gl_FragDepth; — Guarantees the shader will only increase the depth value (push the fragment farther away). This allows the hardware to safely perform Early-Z tests against fragments that would have failed anyway.
  • layout (depth_less) out float gl_FragDepth; — Guarantees the shader will only decrease the depth value (pull the fragment closer).
  • layout (depth_unchanged) out float gl_FragDepth; — Guarantees the value matches gl_FragCoord.z.

Using these qualifiers provides the GPU with enough information to preserve Early-Z culling and Hi-Z functionality, preventing the widespread pipeline stalls caused by unconstrained writes to gl_FragDepth.

Per-Object Velocity Motion Blur in OpenGL

This article explains how to implement motion blur in an OpenGL pipeline using per-object velocity vectors. It details the math and transformations required across consecutive frames, the construction of a dedicated velocity buffer using OpenGL Framebuffer Objects (FBOs), the execution of vertex and fragment shaders to calculate per-pixel motion deltas, and the final post-processing pass that samples the scene color buffer along velocity trajectories to simulate realistic camera exposure.

Understanding Per-Object Velocity Motion Blur

Motion blur simulates the real-world optical effect where objects moving faster than a camera's exposure time appear smeared along their direction of travel. In real-time rendering, simulating physical shutter accumulation per frame is computationally expensive. Instead, modern pipelines generate a screen-space velocity vector for every rendered pixel and use a 2D post-processing blur pass to sample the scene along that vector.

Per-object velocity accounts for dynamic meshes moving relative to the camera, rotating, or deforming, while simultaneously capturing overall camera translation and rotation.

Step 1: Tracking Transformation Matrices

To determine how far a vertex moved since the last frame, you must track two sets of transformations for every dynamic mesh:

  1. Current Frame State:
    • Model Matrix (\(M_{\text{current}}\))
    • View-Projection Matrix (\(VP_{\text{current}}\))
  2. Previous Frame State:
    • Model Matrix (\(M_{\text{previous}}\))
    • View-Projection Matrix (\(VP_{\text{previous}}\))

At the end of each frame render loop, copy the current frame matrices into the previous frame matrix uniform variables before updating them with the new simulation step.

Step 2: The Velocity Vector Shader Pass

Velocity is measured in screen-space (Normalized Device Coordinates, or NDC). The calculation takes place within the geometry rendering stage, often as a render target in a deferred rendering G-buffer or a dedicated pre-pass in forward rendering.

Vertex Shader

The vertex shader calculates both current and previous clip-space positions for the vertex:

#version 330 core

layout(location = 0) in vec3 aPos;

uniform mat4 uCurrentMVP;
uniform mat4 uPreviousMVP;

out vec4 vCurrentPos;
out vec4 vPreviousPos;

void main()
{
    vCurrentPos = uCurrentMVP * vec4(aPos, 1.0);
    vPreviousPos = uPreviousMVP * vec4(aPos, 1.0);
    gl_Position = vCurrentPos;
}

Fragment Shader

In the fragment shader, clip coordinates are mapped to NDC by performing the perspective divide (\(xy / w\)). The difference between the two coordinates yields the 2D velocity vector.

#version 330 core

in vec4 vCurrentPos;
in vec4 vPreviousPos;

layout(location = 0) out vec2 FragVelocity;

void main()
{
    // Convert clip coordinates to NDC [-1, 1]
    vec2 currentNDC = vCurrentPos.xy / vCurrentPos.w;
    vec2 previousNDC = vPreviousPos.xy / vPreviousPos.w;

    // Calculate motion vector and map to UV scale [-0.5, 0.5]
    vec2 velocity = (currentNDC - previousNDC) * 0.5;

    FragVelocity = velocity;
}

Step 3: OpenGL Framebuffer Configuration

The velocity vector requires precision and the ability to store negative numbers. Set up an OpenGL Framebuffer Object (FBO) with a floating-point texture attachment:

  • Format: GL_RG16F or GL_RG32F (two-channel 16-bit or 32-bit floating point).
  • Wrap Mode: GL_CLAMP_TO_EDGE (to avoid sampling artifacts at screen borders).
  • Filter Mode: GL_NEAREST or GL_LINEAR.
GLuint velocityTex;
glGenTextures(1, &velocityTex);
glBindTexture(GL_TEXTURE_2D, velocityTex);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RG16F, screenWidth, screenHeight, 0, GL_RG, GL_FLOAT, NULL);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_EDGE);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_T, GL_CLAMP_TO_EDGE);

glFramebufferTexture2D(GL_FRAMEBUFFER, GL_COLOR_ATTACHMENT1, GL_TEXTURE_2D, velocityTex, 0);

Step 4: The Post-Processing Blur Pass

The final stage renders a full-screen quad. The fragment shader reads the rendered scene color and samples along the direction of the velocity vector retrieved from the velocity texture.

#version 330 core

out vec4 FragColor;
in vec2 TexCoords;

uniform sampler2D uColorTexture;
uniform sampler2D uVelocityTexture;

uniform int uNumSamples;      // Typically 8 to 16
uniform float uBlurScale;     // Controls simulated shutter speed

void main()
{
    vec2 velocity = texture(uVelocityTexture, TexCoords).rg * uBlurScale;

    // Prevent excessive blur from extreme movements
    float maxVelocity = 0.05;
    velocity = clamp(velocity, -maxVelocity, maxVelocity);

    vec4 color = texture(uColorTexture, TexCoords);
    vec2 stepUV = velocity / float(uNumSamples);

    vec2 currentUV = TexCoords;
    for (int i = 1; i < uNumSamples; ++i)
    {
        currentUV += stepUV;
        color += texture(uColorTexture, currentUV);
    }

    FragColor = color / float(uNumSamples);
}

Considerations for Dynamic and Skinned Meshes

  1. Static Objects: For environments that do not move, \(M_{\text{previous}} = M_{\text{current}}\). The velocity vector solely reflects the camera's translation and rotation.
  2. Skinned Meshes: For animated characters, calculating accurate per-vertex velocity requires storing and uploading the previous frame's bone transform matrices in addition to current bone transforms.
  3. Depth Discontinuities: Simple post-processing blur can cause the background to bleed over foreground silhouettes. Comparing the depth values of neighboring samples prevents background pixels from gathering velocity data belonging to foreground objects.

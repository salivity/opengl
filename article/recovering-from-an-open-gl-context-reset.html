Recovering from an OpenGL Context Reset

When an OpenGL context is lost due to a GPU hang, driver crash, or operating system Timeout Detection and Recovery (TDR) event, the application must execute a strict sequence of restoration procedures to resume rendering. This guide outlines the mandatory steps required to recover from a context reset, including querying the reset status, destroying the invalidated context, creating a new context, and fully rebuilding all GPU resources and pipeline states.

1. Detecting the Context Reset

Before recovery can begin, the client application must detect that a reset occurred. When using robust contexts (via GL_ARB_robustness or core OpenGL 4.5+):

  • Periodically call glGetGraphicsResetStatus().
  • Check for return values other than GL_NO_ERROR, specifically GL_GUILTY_CONTEXT_RESET, GL_INNOCENT_CONTEXT_RESET, or GL_UNKNOWN_CONTEXT_RESET.
  • Once a non-zero status is returned, treat the current context as dead; no further drawing commands will be executed by the GPU.

2. Teardown and Platform Context Destruction

Because a context reset invalidates all associated driver-side and GPU-side allocations, the application cannot simply clear and reuse the existing context handle.

  • Detach the lost context from the rendering thread using the platform API (e.g., wglMakeCurrent(NULL, NULL), glXMakeCurrent(..., None), or eglMakeCurrent(..., EGL_NO_CONTEXT)).
  • Explicitly destroy the context using the platform-specific call (wglDeleteContext, glXDestroyContext, or eglDestroyContext).
  • If the underlying window surface was invalidated by the OS compositor during the crash, destroy and re-create the surface or swap chain.

3. Recreating the OpenGL Context

  • Request a new OpenGL context from the platform API using the original context attributes (pixel format, OpenGL version, profile, and robustness flags).
  • Bind the newly created context to the render thread.
  • Re-initialize your OpenGL function pointer loader (e.g., GLAD, GLEW) if your platform or loader binds function addresses to specific context instances.

4. Re-uploading All GPU Resources

A context reset completely purges video memory associated with the application. The client must reallocate and re-upload all persistent assets from host memory or disk:

  • Textures and Samplers: Generate new texture objects (glGenTextures), reallocate storage (glTexStorage* or glTexImage*), and re-upload pixel data alongside mipmaps.
  • Buffer Objects: Re-create Vertex Buffer Objects (VBOs), Index Buffer Objects (IBOs), Uniform Buffer Objects (UBOs), and Shader Storage Buffer Objects (SSBOs). Re-upload their contents from CPU-side memory caches.
  • Shaders and Programs: Recompile all vertex, fragment, compute, and geometry shaders. Re-link all program objects and program pipelines, and re-query uniform locations if dynamic reflection was used.
  • Vertex Array Objects (VAOs): Re-generate VAOs and re-bind vertex buffer formats, attributes, and element buffer associations.
  • Framebuffers (FBOs): Generate new Framebuffer and Renderbuffer objects, allocating storage and re-attaching rebuilt textures or depth/stencil renderbuffers.

5. Re-establishing Pipeline and Global State

OpenGL does not persist global machine state across context recreation. The default state is re-applied, meaning all application-specific configurations must be manually reapplied:

  • Re-enable desired capabilities (e.g., GL_DEPTH_TEST, GL_BLEND, GL_CULL_FACE, GL_STENCIL_TEST).
  • Set blending equations and functions (glBlendFunc, glBlendEquation).
  • Reset depth testing rules (glDepthFunc, glDepthMask).
  • Re-specify viewport and scissor regions (glViewport, glScissor).
  • Clear all buffers to clear colors/values to initialize the first frame.

6. Synchronizing Application Logic

  • Invalidate any engine-level cache layers (e.g., internal state-trackers that skip redundant glBindTexture or glUseProgram calls) to match the true baseline state of the fresh context.
  • Destroy and regenerate synchronization objects such as GLsync fence primitives and timer queries.
  • Reset frame counters, frame timers, or presentation pacing systems to prevent large delta-time spikes caused by the recovery pause.

OpenGL Immediate Mode: glBegin and glEnd Explained

Immediate mode rendering was the foundational paradigm of early OpenGL, characterized by the direct submission of vertex and attribute data from the CPU to the GPU between pairs of glBegin and glEnd function calls. This article provides a comprehensive overview of how immediate mode functioned, its programming mechanics, the severe performance bottlenecks that led to its obsolescence, and how modern retained-mode paradigms eventually replaced it.

The Concept of Immediate Mode

In early graphics programming, "immediate mode" meant that the graphics hardware did not retain geometry data across frames. Instead, the client application was responsible for transmitting vertex coordinates, colors, normals, and texture coordinates to the graphics pipeline sequentially every single frame.

The OpenGL state machine processed these commands immediately upon receipt. As soon as the application issued a vertex command, the pipeline transformed the vertex, lit it according to current state parameters, and readied it for rasterization. The GPU did not store the mesh in dedicated video memory (VRAM) between render cycles.

How glBegin and glEnd Worked

The glBegin and glEnd delimiters formed the core of immediate mode rendering. The glBegin function accepted a primitive type token—such as GL_TRIANGLES, GL_QUADS, GL_LINES, or GL_POLYGON—which told the driver how to interpret the sequence of vertices that followed. The glEnd function signaled the completion of that primitive group.

Within the block, developers called a series of state-setting commands and vertex definitions:

glBegin(GL_TRIANGLES);
    glColor3f(1.0f, 0.0f, 0.0f);   // Sets current color state to red
    glVertex3f(-0.5f, -0.5f, 0.0f); // Vertex 1

    glColor3f(0.0f, 1.0f, 0.0f);   // Sets current color state to green
    glVertex3f(0.5f, -0.5f, 0.0f);  // Vertex 2

    glColor3f(0.0f, 0.0f, 1.0f);   // Sets current color state to blue
    glVertex3f(0.0f, 0.5f, 0.0f);   // Vertex 3
glEnd();

Because OpenGL acts as a state machine, any attribute set prior to a glVertex call (such as glColor, glNormal, or glTexCoord) applied to that vertex. Calling glVertex finalized the attribute set and pushed the complete vertex down the pipeline.

Architectural Bottlenecks

While immediate mode was conceptually simple and easy to learn, it became a massive performance bottleneck as 3D scenes grew in complexity:

  • High Function Call Overhead: Defining a model with 100,000 triangles required hundreds of thousands of individual function calls per frame across the CPU-GPU boundary. The CPU spent most of its time executing function dispatch logic rather than calculating game logic.
  • Bus Saturation: Geometry data had to travel across the system bus (AGP or PCI Express) on every frame. Because the GPU did not cache the geometry in VRAM, the bus bandwidth was easily saturated.
  • Lack of Parallelism: Modern GPUs rely on massively parallel architectures that process thousands of vertices simultaneously. Feeding vertices one by one via procedural function calls prevented the GPU from operating at peak efficiency.

Deprecation and the Move to Retained Mode

To solve these hardware mismatches, OpenGL evolved toward retained mode rendering. The transition began with client-side Vertex Arrays in OpenGL 1.1, which allowed applications to submit arrays of data with a single call.

OpenGL 1.5 introduced Vertex Buffer Objects (VBOs), enabling applications to upload vertex data directly into GPU-accessible VRAM once and draw it repeatedly with minimal CPU intervention. By the release of OpenGL 3.0, the glBegin and glEnd immediate mode paradigm was marked deprecated, and it was entirely removed from the core profile in OpenGL 3.1. Today, modern graphics APIs—including modern OpenGL, Vulkan, and DirectX 12—rely exclusively on buffer-backed, retained memory models managed via programmable shaders.

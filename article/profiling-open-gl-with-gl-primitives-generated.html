Profiling OpenGL with GL_PRIMITIVES_GENERATED

The GL_PRIMITIVES_GENERATED query in OpenGL is an essential hardware profiling metric used to measure the exact number of geometric primitives emitted by the pipeline before rasterization and clipping occur. This article explores how this query functions, where it fits within the modern graphics pipeline, and why it is indispensable for diagnosing geometry bottlenecks, validating algorithmic amplification, and optimizing Level of Detail (LOD) systems.

Understanding GL_PRIMITIVES_GENERATED

When profiling OpenGL applications, developers often struggle to pinpoint whether performance drops stem from heavy vertex processing, excessive rasterization, or fill-rate limitations. The GL_PRIMITIVES_GENERATED query counter increments every time a primitive—such as a point, line, or triangle—is successfully produced by the geometry processing stages.

Specifically, this query records primitives output by:

  • The Vertex Shader (when Geometry and Tessellation stages are omitted).
  • The Tessellation Evaluation Shader (when the Geometry Shader is omitted).
  • The Geometry Shader (when present).

Because the counter is evaluated immediately after these programmable stages, it captures geometry prior to viewport clipping, frustum culling, and back-face culling performed by the fixed-function hardware.

Diagnostic Significance in GPU Profiling

Using GL_PRIMITIVES_GENERATED provides actionable data across several optimization scenarios:

1. Measuring Geometry Shader and Tessellation Amplification

Geometry shaders and tessellation stages can dynamically generate new primitives from incoming data. An unoptimized shader might inadvertently generate millions of micro-triangles, saturating memory bandwidth and stalling execution units. By wrapping draw calls inside a GL_PRIMITIVES_GENERATED query, developers can calculate the precise amplification factor (output primitives divided by input primitives) and tune shader parameters to prevent geometry explosions.

2. Evaluating Culling and Level of Detail (LOD) Efficiency

Effective rendering engines employ CPU-side or compute-based frustum and occlusion culling to reduce the workload sent to the rendering pipeline. By tracking GL_PRIMITIVES_GENERATED, you can verify whether your LOD transitions properly reduce geometric complexity at distance and confirm that culled objects are not being submitted to the GPU.

3. Comparing Against Written Primitives

A common optimization technique pairs GL_PRIMITIVES_GENERATED with GL_TRANSFORM_FEEDBACK_PRIMITIVES_WRITTEN. If transform feedback buffer sizes are insufficient or buffer-overflow conditions occur, comparing these two query results immediately highlights data truncation issues, as GL_PRIMITIVES_GENERATED reports what was intended to be output, while the transform feedback query reports what successfully fit into memory.

Basic Query Implementation

To integrate the query into a render loop, instantiate a query object and bracket the relevant draw calls:

GLuint queryId;
glGenQueries(1, &queryId);

// Begin recording primitive generation
glBeginQuery(GL_PRIMITIVES_GENERATED, queryId);

// Execute draw calls
glDrawElements(GL_TRIANGLES, indexCount, GL_UNSIGNED_INT, 0);

// End recording
glEndQuery(GL_PRIMITIVES_GENERATED);

// Retrieve results asynchronously to prevent CPU stalls
GLuint64 primitivesCount = 0;
glGetQueryObjectui64v(queryId, GL_QUERY_RESULT, &primitivesCount);

To avoid stalling the CPU while waiting for the GPU to finish execution, query results should typically be fetched one or two frames later using asynchronous buffering patterns.

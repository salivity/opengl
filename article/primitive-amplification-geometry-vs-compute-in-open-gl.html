Primitive Amplification: Geometry vs Compute in OpenGL

This article evaluates primitive amplification in OpenGL, comparing traditional hardware-managed amplification via Geometry Shaders against modern compute-driven pipelines using Compute Shaders, Shader Storage Buffer Objects (SSBOs), and indirect draw calls. It breaks down the architectural bottlenecks of legacy geometry stages, explains how compute-driven workflows overcome these limitations through explicit memory control and SIMD lane utilization, and provides clear criteria for choosing the optimal approach in real-time rendering.

The Traditional Model: Geometry Shaders

Geometry Shaders (GS) were introduced to standard pipelines to allow dynamic topology changes and primitive amplification directly on the GPU. Operating between the vertex processing and rasterization stages, a geometry shader takes a single primitive (such as a point or triangle) and emits zero, one, or multiple primitives using built-in functions like EmitVertex() and EndPrimitive().

Despite their conceptual simplicity, geometry shaders suffer from severe architectural limitations:

  • Variable Output Sizing: Hardware needs to allocate internal execution buffers based on max_vertices. If a shader declares a high maximum output count but emits only a few vertices on average, internal register and cache allocation becomes severely unbalanced.
  • SIMD Inefficiency: GPUs execute work in lockstep (warps or wavefronts). Because different threads within a warp can emit differing numbers of vertices, threads with fewer emissions idle while waiting for the heaviest thread to finish, causing significant lane divergence and stalling.
  • Internal Buffer Bottlenecks: Amplified primitives must be stored in specialized on-chip FIFO queues before reaching the rasterizer. When amplification factors are high, these queues saturate, causing pipeline backpressure that stalls upstream vertex processing.

The Modern Model: Compute-Driven Amplification

Modern OpenGL pipelines decouple geometry generation from the fixed-function rasterization sequence by using Compute Shaders combined with indirect rendering (glDrawArraysIndirect or glDrawElementsIndirect).

In this model, amplification is handled as a parallel data transformation task:

  1. Parallel Evaluation: A compute shader processes source data (such as point grids, control curves, or coarse meshes) across tightly scheduled workgroups.
  2. Buffer Generation: The compute shader writes generated index and vertex data into an SSBO or Vertex Buffer Object (VBO).
  3. Atomic Counting: A workgroup or invocation uses atomic counters (atomicAdd) to track the exact number of primitives produced, writing the final counts directly into a dispatch or indirect draw command buffer.
  4. Execution: OpenGL executes an indirect draw call that reads parameters directly from GPU memory, bypassing CPU round-trips entirely.

Key Architectural Comparisons

1. Hardware Utilization and Scheduling

Geometry shaders run on specialized pipeline hooks bound to the primitive distributor. High amplification factors introduce serialization because primitive ordering must strictly adhere to the input stream. Compute shaders, by contrast, utilize the GPU's general compute engine. Threads execute independently without the requirement to preserve raster order until the final draw call, allowing modern GPU schedulers to achieve near-100% compute unit occupancy.

2. Memory Bandwidth and Cache Behavior

  • Geometry Shaders: Data flowing from a geometry shader to the rasterizer resides in limited, vendor-specific on-chip cache. If this cache overflows, performance drops sharply as data spills to main VRAM under unoptimized access patterns.
  • Compute Shaders: Data is written explicitly to SSBOs using coalesced global memory operations. Developers control cache behavior via memory barriers (glMemoryBarrier(GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT | GL_COMMAND_BARRIER_BIT)), optimizing bandwidth for subsequent vertex fetch stages.

3. Algorithmic Flexibility

Compute-driven pipelines allow multi-pass data amplification algorithms. A developer can compute complex operations—such as parallel prefix sums (stream compaction), hierarchical level of detail (LOD) selection, and frustum/occlusion culling—in the same pass that primitives are generated. Geometry shaders are restricted to single-pass, per-primitive evaluation with no inter-thread communication across different primitive inputs.

Summary: When to Use Each

  • Use Geometry Shaders: Only for specialized, low-amplification tasks that benefit from hardware-wired state routing, such as rendering cubemaps in a single pass using gl_Layer, generating debug visualizers (e.g., surface normals), or maintaining legacy engines where refactoring the render graph into multiple passes is impractical.
  • Use Compute-Driven Approaches: For all production-scale amplification tasks, including particle billboarding, procedural geometry generation, marching cubes/isosurfaces, dynamic terrain subdivision, and GPU-driven culling pipelines. Compute shaders provide predictable execution times, higher peak throughput, and seamless integration with modern GPU design.

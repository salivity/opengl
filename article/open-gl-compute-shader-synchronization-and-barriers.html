OpenGL Compute Shader Synchronization and Barriers

OpenGL compute shaders execute workloads across thousands of parallel invocations, requiring explicit synchronization to avoid race conditions and ensure data integrity. This article provides a comprehensive overview of the synchronization mechanisms in OpenGL, covering intra-workgroup execution barriers, GLSL memory barriers, the coherent type qualifier, host-level memory barriers via glMemoryBarrier, and CPU-GPU synchronization using fence sync objects.

Intra-Workgroup Synchronization (GLSL)

Compute shaders group invocations into local workgroups. Invocations within the same local workgroup can communicate via shared variables, but their execution order is non-deterministic. To coordinate them, GLSL provides intra-workgroup barriers:

  • barrier(): Acts as both an execution barrier and a shared memory barrier. Every invocation in the local workgroup must reach this call before any invocation is permitted to proceed beyond it. Additionally, any writes to shared variables executed before the barrier() call are guaranteed to be visible to all invocations in the workgroup after the barrier.
  • memoryBarrierShared(): Enforces ordering for memory transactions specifically targeting shared memory variables without halting execution flow. It guarantees that writes to shared memory prior to the call are committed before subsequent writes.
  • groupMemoryBarrier(): Provides a memory barrier ordering for all memory accesses (both shared variables and global buffers) relative to the calling invocation, limited to the scope of the local workgroup.

Memory Coherency and GLSL Memory Barriers

By default, the OpenGL shader execution model assumes memory operations are weakly ordered. Writes to Shader Storage Buffer Objects (SSBOs) or images are cached per execution unit and are not automatically visible across different invocations or across workgroups.

The coherent Qualifier

When buffer variables or image variables are declared, they should use the coherent qualifier if multiple invocations read and write to the same memory addresses:

layout(std430, binding = 0) coherent buffer OutputData {
    uint counter;
    float values[];
};

The coherent qualifier signals to the compiler and hardware that accesses to this memory must bypass local caches or be tracked so that updates can become visible to other invocations.

GLSL Memory Barrier Functions

To force pending writes to flush to memory accessible by other invocations, use targeted GLSL memory barrier functions:

  • memoryBarrier(): Flushes pending writes across all memory types (buffers, images, shared variables).
  • memoryBarrierBuffer(): Ensures that all memory transactions on buffer variables (such as SSBOs or atomic counters) initiated prior to the call are committed to memory.
  • memoryBarrierImage(): Ensures that all texture image stores (imageStore) initiated prior to the call are committed.
  • memoryBarrierAtomicCounter(): Flushes updates made to atomic counter buffers.

Host-Side Synchronization: glMemoryBarrier

GLSL barriers only coordinate invocations within a single dispatch. When subsequent OpenGL commands (such as a draw call, texture sample, or another compute dispatch) depend on data produced by a compute shader, the host application must call glMemoryBarrier.

glMemoryBarrier defines a barrier between shader writes and subsequent read operations performed by specific OpenGL pipeline stages. It accepts a bitfield indicating which subsequent operations must wait for pending memory writes to complete:

  • GL_SHADER_STORAGE_BARRIER_BIT: Ensures SSBO writes from the compute shader are visible to subsequent shader read operations (including subsequent compute dispatches).
  • GL_TEXTURE_FETCH_BARRIER_BIT: Ensures image or buffer writes are visible when sampled as textures via sampler* in subsequent rendering passes.
  • GL_SHADER_IMAGE_ACCESS_BARRIER_BIT: Ensures image writes are visible to subsequent imageLoad and imageStore operations.
  • GL_FRAMEBUFFER_BARRIER_BIT: Ensures writes are visible when the target memory is subsequently used as a framebuffer attachment.
  • GL_ELEMENT_ARRAY_BARRIER_BIT: Ensures buffer writes are visible when the buffer is bound as an index array (GL_ELEMENT_ARRAY_BUFFER).
  • GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT: Ensures buffer writes are visible when the buffer provides vertex attributes.
  • GL_COMMAND_BARRIER_BIT: Ensures data written into a buffer used for indirect dispatch or draw commands (such as glDispatchComputeIndirect or glDrawArraysIndirect) is visible before execution.
  • GL_ALL_BARRIER_BITS: Flushes all pending writes to be visible to all subsequent pipeline operations. While convenient, it can introduce pipeline stalls and should be avoided if performance is critical.

A typical sequence between compute and rendering:

// Dispatch compute work
glDispatchCompute(numGroupsX, numGroupsY, numGroupsZ);

// Ensure compute writes to the SSBO are visible before drawing
glMemoryBarrier(GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT);

// Render using the generated buffer data
glBindVertexArray(vao);
glDrawArrays(GL_TRIANGLES, 0, vertexCount);

CPU-GPU Synchronization: Sync Objects

If the CPU needs to read compute shader results via functions like glGetBufferSubData or glMapBufferRange, memory barriers alone are insufficient because glMemoryBarrier only synchronizes internal GPU pipeline stages.

To synchronize between the CPU and GPU:

  1. Insert a Fence: Call glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE, 0) immediately after your dispatch and pipeline barrier calls.
  2. CPU Wait: Call glClientWaitSync(syncObject, GL_SYNC_FLUSH_COMMANDS_BIT, timeoutNanoseconds) to block the CPU thread until the GPU finishes all operations prior to the fence.
  3. GPU-Side Stalls (Optional): If you need the GPU command queue itself to halt without blocking the CPU, use glWaitSync.
  4. Clean Up: Delete the sync object when no longer needed using glDeleteSync(syncObject).

OpenGL SSBO Readonly Qualifier Cache Optimizations

In OpenGL, declaring a Shader Storage Buffer Object (SSBO) with the readonly qualifier informs the graphics driver and hardware compiler that the shader stage will strictly perform load operations on that resource. This explicit guarantee allows the GPU to bypass expensive write-coherence protocols, route memory accesses through high-bandwidth read-only texture and scalar caches, emit specialized hardware load instructions, and perform aggressive latency-hiding optimizations that would otherwise be unsafe for read-write memory.

Bypassing Cache Coherence Overhead

By default, SSBOs are assumed to be read-write, forcing the GPU memory architecture to handle potential data hazards. Read-write access requires the hardware to maintain coherence across execution units (such as compute workgroups or fragment warps/wavefronts). This often means write-back or write-through policies must be enforced, dirty cache lines must be tracked, and local caches may need frequent invalidation or complete bypass to prevent reading stale data.

Applying readonly eliminates data hazards originating from that shader stage. Because the shader cannot mutate the buffer, the driver can safely disable coherence checks and cache invalidation routines for those memory addresses during execution, leading to significantly higher cache hit rates.

Routing Through Dedicated Read-Only Caches

Modern GPU architectures feature split cache hierarchies optimized for different workload types:

  • Read-Write Caches: These are built with complex logic to handle atomic operations, synchronization, and store operations. They often sacrifice raw bandwidth and hit latency to ensure correct memory ordering across compute units.
  • Read-Only / Texture Caches: These caches (often tied to the texture mapping units or scalar pipelines) are optimized for massive spatial locality, high parallel throughput, and read bandwidth.

When an SSBO lacks the readonly qualifier, the compiler must route memory loads through the general-purpose, read-write L1/L2 data cache path. Markings such as readonly allow the shader compiler to route memory requests through the read-only texture cache or dedicated scalar constant caches (such as AMD's Scalar L1 or NVIDIA's texture/uniform caches). These read paths feature wider buses and can serve multiple threads concurrently with lower latency.

Instruction Selection and Cache Flags

Hardware instruction sets (ISAs) feature specific flags on load instructions that dictate caching behavior. When the GLSL compiler translates intermediate code to GPU assembly:

  1. Cache Line Allocation Flags: A read-write load may be instructed to bypass the L1 cache entirely to avoid cache pollution, fetching directly from L2 or VRAM. A readonly load allows the compiler to set flags that permit caching in all levels of the hierarchy (e.g., caching in both L1 and L2).
  2. Vectorized and Scalar Loads: If the driver detects uniform read access across an invocation group, readonly enables the use of specialized scalar load hardware instead of divergent vector load instructions, dramatically reducing register pressure and memory pipeline congestion.

Aggressive Compiler Scheduling and Prefetching

Memory loads are among the highest-latency operations a GPU executes. To hide this latency, the shader compiler attempts to hoist loads as early as possible in the instruction stream (prefetching) to give memory controllers time to fetch data before it is consumed.

In a mutable buffer, the compiler must treat stores as potential barriers; it cannot safely hoist a load above a store if their addresses might alias. The readonly qualifier guarantees that no stores to the buffer will occur within the shader, allowing the compiler's instruction scheduler to aggressively reorder and hoist memory reads to maximize latency hiding.

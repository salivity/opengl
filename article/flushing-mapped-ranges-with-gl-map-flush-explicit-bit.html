Flushing Mapped Ranges with GL_MAP_FLUSH_EXPLICIT_BIT

When updating OpenGL buffer objects using glMapBufferRange, setting the GL_MAP_FLUSH_EXPLICIT_BIT flag changes how modifications are committed to GPU memory. Instead of the driver automatically copying the entire mapped region upon unmapping, this flag explicitly transfers synchronization responsibility to the application. Failing to manually flush modified regions via glFlushMappedBufferRange leaves the driver unaware of memory writes, resulting in stale data, visual corruption, or undefined rendering behavior.

Default Mapping vs. Explicit Flushing

By default, when a buffer is mapped with write access (GL_MAP_WRITE_BIT) and subsequently unmapped with glUnmapBuffer, the OpenGL implementation assumes the entire mapped region has been altered. The driver automatically flushes the entire range to make the new contents visible to the GPU.

While convenient, this default behavior introduces severe performance overhead if an application maps a large buffer (e.g., several megabytes) but only modifies a tiny fraction (such as updating a single matrix or a few vertices). Flushing the entire region forces unnecessary memory bus traffic and cache management overhead.

The Contract of GL_MAP_FLUSH_EXPLICIT_BIT

Including GL_MAP_FLUSH_EXPLICIT_BIT in the access flags establishes a strict contract between the application and the graphics driver:

  1. Automatic Flushes Are Disabled: Calling glUnmapBuffer will no longer signal the driver to synchronize the mapped memory back to the GPU.
  2. Explicit Range Notification Is Required: The application must notify the driver of the exact byte sub-ranges that were modified by calling glFlushMappedBufferRange.
  3. Driver Optimization: The GPU driver only invalidates, synchronizes, or transfers the exact sub-allocations identified by those explicit flush calls.

Why Flushing Is Critical

If memory is modified while GL_MAP_FLUSH_EXPLICIT_BIT is active and the application unmaps the buffer without calling glFlushMappedBufferRange, the driver will never push the dirty cache lines or DMA transfer commands to the hardware.

The consequences include:

  • Stale Reads: The GPU continues reading the previous contents of the buffer because the host writes remain trapped in CPU caches or unsynchronized staging memory.
  • Partial or Intermittent Updates: Depending on the underlying architecture (such as unified memory architectures versus discrete GPUs), some writes may leak through via CPU cache line evictions while others do not, causing sporadic and hard-to-debug visual glitches.
  • Undefined Buffer Contents: OpenGL specifications classify reading unflushed areas that were explicitly mapped for writing as undefined behavior.

Proper Implementation Pattern

To safely write data with explicit flushing, use the following sequence:

  1. Map the buffer specifying write access and explicit flushing:

    void* ptr = glMapBufferRange(GL_ARRAY_BUFFER, 0, totalBufferSize, 
                             GL_MAP_WRITE_BIT | GL_MAP_FLUSH_EXPLICIT_BIT);

  2. Write only to the desired slice of memory:

    memcpy((char*)ptr + updateOffset, newDataSource, updateSize);

  3. Inform OpenGL of the exact region modified relative to the start of the mapped buffer:

    glFlushMappedBufferRange(GL_ARRAY_BUFFER, updateOffset, updateSize);

  4. Unmap the buffer once all updates and flushes are complete:

    glUnmapBuffer(GL_ARRAY_BUFFER);

Flushing mapped ranges guarantees that explicit, fine-grained updates achieve optimal bus bandwidth efficiency without sacrificing data integrity on the GPU.

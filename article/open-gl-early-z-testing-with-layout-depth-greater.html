OpenGL Early-Z Testing with layout(depth_greater)

Modifying the depth value of a fragment within an OpenGL fragment shader usually disables the GPU's Early-Z (early depth testing) optimizations, causing significant performance degradation. By declaring the layout(depth_greater) qualifier, developers provide a compile-time guarantee to the hardware about how gl_FragDepth will change relative to the interpolated depth. This article explains how this guarantee allows the GPU driver to safely perform conservative early depth rejection, saving processing power without producing visual artifacts.

The Problem: Why Writing to gl_FragDepth Disables Early-Z

Under normal rendering conditions, modern GPUs run depth tests before executing the fragment shader—a feature known as Early-Z. If a fragment is occluded by geometry already rendered into the depth buffer, it is discarded immediately, saving the computational cost of running the fragment shader.

When a shader explicitly writes to gl_FragDepth, the pipeline encounters a dependency: it cannot know the fragment's final depth value until the fragment shader finishes executing. Consequently, the GPU is forced to disable Early-Z and revert to late depth testing. Every fragment must run its full shader program, even if it is completely hidden behind other geometry.

The Contract of layout(depth_greater)

The layout(depth_greater) layout qualifier, introduced in OpenGL 4.2 via the ARB_conservative_depth extension, creates a contract between your shader and the GPU pipeline. It specifies that any value written to gl_FragDepth will be strictly greater than or equal to the fixed-function interpolated depth (gl_FragCoord.z).

#version 420 core
layout (depth_greater) out float gl_FragDepth;

void main()
{
    // The assigned depth must be >= gl_FragCoord.z
    gl_FragDepth = gl_FragCoord.z + 0.05;
}

How It Restores Early Depth Rejection

Most 3D applications use standard reverse-order depth comparisons, where nearer objects have smaller depth values and the depth comparison function is set to GL_LESS or GL_LEQUAL. In this setup, a fragment only passes if its depth is smaller than the current depth buffer value.

Because layout(depth_greater) guarantees that the fragment's final depth will only increase (move further away), the GPU can perform a conservative early depth test using the initial gl_FragCoord.z:

  1. Early Test Evaluation: The GPU checks the incoming, unmodified fragment depth (gl_FragCoord.z) against the current depth buffer value using the active depth function (GL_LESS or GL_LEQUAL).
  2. Deterministic Failure: If the unmodified depth fails the test (meaning it is already deeper than the existing pixel), the fragment can never pass. Since the shader is only permitted to make the depth value larger, executing the shader could not possibly yield a passing result.
  3. Early Discard: The GPU immediately drops the fragment prior to running the fragment shader.

If the fragment passes this early check, the GPU must still execute the fragment shader to compute the true, modified depth value, after which the new value is written to the depth buffer during the late stage.

Constraints and Considerations

  • Depth Comparison Function: The performance benefit of layout(depth_greater) relies on using GL_LESS or GL_LEQUAL. If an application uses an inverted depth buffer (GL_GREATER or GL_GEQUAL), the inverse qualifier—layout(depth_less)—is required to achieve early depth rejection.
  • Driver Enforcement: Violating the qualifier contract (for instance, writing a depth value smaller than gl_FragCoord.z while using depth_greater) results in undefined behavior, which often manifests as severe visual artifacts or flickering geometry due to fragments being discarded prematurely.

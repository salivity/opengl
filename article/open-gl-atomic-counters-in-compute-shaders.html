OpenGL Atomic Counters in Compute Shaders

This article provides a comprehensive overview of OpenGL atomic counters and their implementation within compute shaders. It explores the definition of atomic counters, their underlying hardware mechanisms, and how they solve race conditions in massively parallel environments. Readers will learn the essential GLSL functions, host-side API configuration, synchronization requirements, and practical use cases such as stream compaction and dynamic memory allocation.

What Are OpenGL Atomic Counters?

OpenGL atomic counters are specialized, hardware-accelerated integer variables stored in GPU memory that allow multiple shader invocations to read and modify a shared scalar value concurrently without race conditions. In a standard shader execution, parallel threads reading and writing to the same memory location simultaneously produce undefined results due to memory hazards. Atomic counters solve this by serializing read-modify-write operations at the hardware level, ensuring that each thread executes its operation completely before the next thread accesses the counter.

Atomic counters are backed by a dedicated buffer object known as an Atomic Counter Buffer Object (ACBO), or mapped to standard Uniform Buffer Objects (UBO) or Shader Storage Buffer Objects (SSBO). In GLSL, they are represented by the atomic_uint opaque data type and are restricted to 32-bit unsigned integers.

Implementation in GLSL Compute Shaders

Compute shaders operate in work-groups across a multi-threaded grid. To use an atomic counter, you declare it as a uniform variable bound to a specific buffer binding point using the layout qualifier:

#version 430 core

layout(local_size_x = 256) in;

// Declare the atomic counter at binding point 0
layout(binding = 0) uniform atomic_uint globalCounter;

void main() {
    // Atomically increment the counter and retrieve the previous value
    uint index = atomicCounterIncrement(globalCounter);
    
    // Use the unique index for writing to an output array
}

Core Built-in GLSL Functions

GLSL provides several built-in functions to interact with atomic_uint variables:

  • atomicCounterIncrement(atomic_uint c): Atomically increments the counter by 1 and returns the value before the increment.
  • atomicCounterDecrement(atomic_uint c): Atomically decrements the counter by 1 and returns the value after the decrement.
  • atomicCounter(atomic_uint c): Reads and returns the current value of the counter without modifying it.
  • atomicCounterAdd(atomic_uint c, uint data) (via extensions or GLSL 4.6): Adds an arbitrary unsigned integer value to the counter.
  • atomicCounterSubtract(atomic_uint c, uint data): Subtracts an arbitrary unsigned integer value from the counter.

Host-Side Setup in OpenGL

To supply data to the atomic counter in a compute shader, an application must allocate, initialize, and bind an OpenGL buffer on the CPU side:

  1. Generate and Allocate the Buffer:

    GLuint counterBuffer;
glGenBuffers(1, &counterBuffer);
glBindBuffer(GL_ATOMIC_COUNTER_BUFFER, counterBuffer);

// Allocate 4 bytes for a single 32-bit unsigned integer initialized to 0
GLuint initialValue = 0;
glBufferData(GL_ATOMIC_COUNTER_BUFFER, sizeof(GLuint), &initialValue, GL_DYNAMIC_DRAW);

  2. Bind to the Indexed Binding Point:

    // Bind to index 0, matching layout(binding = 0) in the shader
glBindBufferBase(GL_ATOMIC_COUNTER_BUFFER, 0, counterBuffer);

  3. Resetting the Counter: Counters do not reset automatically between dispatch calls. Resetting requires re-uploading data using glBufferSubData or clearing the buffer with glClearBufferData.

Synchronization and Memory Barriers

Because atomic counters involve asynchronous execution across distinct work-groups, accessing the final result requires proper memory synchronization.

If a subsequent shader pass, draw call, or the CPU needs to read from the counter or the data written using the counter's indices, you must invoke a memory barrier:

glMemoryBarrier(GL_ATOMIC_COUNTER_BARRIER_BIT | GL_SHADER_STORAGE_BARRIER_BIT);

Within a compute shader, invocations in the same work-group can coordinate using the memoryBarrierAtomicCounter() function alongside barrier() to enforce ordering between counter updates and shared memory writes.

Common Use Cases

  • Stream Compaction: When filtering an input dataset (such as culling invisible geometry), compute threads increment an atomic counter only if their element meets a condition. The returned index serves as the output write location, packing valid items densely into an array.
  • Histogram Generation: Counting the frequency of values (such as pixel luminance) across massive datasets by incrementing indexed counter bins.
  • Dynamic Work Allocation: Serving as a global work queue index where idle compute threads atomically pull tasks from a shared list.

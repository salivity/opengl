Half-Float in OpenGL: Reduce Vertex Attribute Memory

The half-float data type (16-bit floating-point) reduces memory footprints in OpenGL attribute arrays by cutting per-component storage requirements in half compared to standard 32-bit single-precision floats. This reduction directly shrinks Vertex Buffer Object (VBO) sizes, reduces graphics memory consumption, conserves memory bandwidth between the GPU and VRAM, and enhances cache utilization during vertex fetching. This guide explains the mechanics of GL_HALF_FLOAT, how it optimizes the rendering pipeline, and where it can be applied effectively.

The Storage Mechanics: 32-Bit vs. 16-Bit

Standard floating-point numbers (GL_FLOAT) adhere to the IEEE 754 standard for single precision, consuming 32 bits (4 bytes) per component:

  • 1 sign bit
  • 8 exponent bits
  • 23 mantissa (fraction) bits

The half-float format (GL_HALF_FLOAT) compresses this representation into 16 bits (2 bytes) per component:

  • 1 sign bit
  • 5 exponent bits
  • 10 mantissa bits

By halving the byte count per scalar, any vertex attribute using half-floats requires 50% less physical memory. For a standard 3D mesh containing positions, normals, and texture coordinates, converting non-position attributes to 16-bit floats significantly reduces the overall stride of the vertex structure.

Practical Impact on Vertex Buffer Arrays

Consider a typical vertex structure defined with standard floats:

struct Vertex {
    float position[3]; // 12 bytes
    float normal[3];   // 12 bytes
    float texCoord[2]; // 8 bytes
}; // Total: 32 bytes per vertex

A model with 1,000,000 vertices using this layout requires 32 MB of VRAM.

By transitioning appropriate attributes to half-precision:

struct VertexOptimized {
    float position[3];          // 12 bytes (maintained for precision)
    unsigned short normal[3];   // 6 bytes (half-float)
    unsigned short texCoord[2]; // 4 bytes (half-float)
    unsigned short padding;     // 2 bytes (alignment)
}; // Total: 24 bytes per vertex

The memory footprint drops to 24 MB, yielding an immediate 25% reduction in total buffer size for the mesh. If positions can also safely use half-floats (such as in local object space for smaller assets), the footprint falls to 16 bytes per vertex—a 50% overall memory reduction.

Bandwidth and Cache Efficiency

The primary performance bottleneck in vertex processing is frequently memory bandwidth rather than compute capability. The GPU's vertex fetch stage must stream vertex data from memory into the shader cores.

  1. Reduced Bandwidth Consumption: Loading 16-bit values transfers half the data over the memory bus per attribute, preventing saturation during high-geometry scenes.
  2. Improved Vertex Cache Hit Rates: Smaller vertex strides allow more vertices to fit inside the GPU's L1/L2 caches and post-transform caches. This maximizes cache hits, reducing the need to re-fetch redundant data for shared vertices across indexed triangles.

Implementation in OpenGL

OpenGL supports half-floats natively through core specifications (and via extensions like OES_vertex_half_float in older OpenGL ES environments). Half-floats are declared in the attribute pointer configuration using GL_HALF_FLOAT.

To bind an attribute array containing half-precision data:

// Example: Normal vector with 3 half-float components
glVertexAttribPointer(
    normalAttributeLocation, 
    3,                  // Number of components (x, y, z)
    GL_HALF_FLOAT,      // Data type
    GL_FALSE,           // Normalized (typically false for floats)
    sizeof(VertexOptimized), 
    (void*)offsetof(VertexOptimized, normal)
);

Hardware modern enough to support programmable shaders unpacks these 16-bit values automatically into standard 32-bit registers inside the vertex shader, meaning shader calculations retain high precision without requiring custom decompression code.

Best Practices and Precision Trade-Offs

While half-floats substantially lower memory footprints, the reduced dynamic range (±65,504) and precision (~3.3 decimal digits) require selective application:

  • Ideal for Half-Floats:
    • Texture Coordinates (UVs): Most standard UV mapping stays within the 0.0 to 1.0 range, where half-float precision is more than adequate to prevent texture swimming.
    • Normals and Tangents: Unit vectors always remain within the range of [-1.0, 1.0], making them optimal candidates for half-precision storage.
    • Vertex Colors: Linear RGB values easily fit within the range and precision of 16-bit floats.
  • Use Caution With:
    • World-Space Positions: Large-scale environments will suffer from visible vertex jitter (quantization artifacts) due to the limited mantissa precision. Keep positions in standard 32-bit floats, or restrict half-float positions strictly to localized, normalized object-space models.

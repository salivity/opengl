How to Share Textures Between OpenGL Contexts

Sharing texture assets between an off-screen rendering context and a visible display context allows applications to perform heavy asset generation or asynchronous loading in the background without dropping frames on the main rendering thread. Achieving this safely requires establishing context sharing during creation, respecting OpenGL's single-thread-per-context rule, and utilizing explicit synchronization primitives to prevent pipeline race conditions. This guide outlines the mechanics of context sharing, synchronization via sync fences, and safe resource lifecycle management.

Context Creation and Association

OpenGL contexts do not share resources by default. Shared access must be established at the operating system or windowing API level when creating the off-screen context:

  • EGL (Android, Linux Wayland, Embedded): Pass the display context handle to eglCreateContext as the share_context parameter.
  • WGL (Windows): Create both contexts and link them using wglShareLists(hglrcVisible, hglrcOffscreen).
  • GLX (Linux X11): Pass the visible context as the share_list parameter to glXCreateContext or glXCreateNewContext.
  • CGL / NSOpenGL (macOS): Use a shared CGLPixelFormatObj or an explicit NSOpenGLContext sharing group.

Once linked, texture objects, buffer objects, and shaders are shared across both contexts. However, container objects—specifically Framebuffer Objects (FBOs) and Vertex Array Objects (VAOs)—are context-local and cannot be shared.

Thread Affinity

An active OpenGL context can only be bound to a single thread at any given time using glMakeCurrent (or its platform equivalent). The visible context typically lives on the main render thread, driving the display. The off-screen context lives on a background worker thread where heavy workloads (e.g., video decoding, procedurally generated textures, or texture baking) execute.

Never attempt to bind the same context across multiple threads simultaneously, as this results in undefined behavior and immediate driver crashes.

Safe Synchronization Using Sync Objects

OpenGL execution is asynchronous; submitting commands to the off-screen context does not mean the GPU has finished processing them. Reading a shared texture on the display thread while the worker thread is still writing to it causes race conditions and visual artifacts (tearing or incomplete rendering).

To synchronize the two contexts safely without stalling the CPU with expensive calls like glFinish():

  1. Render in the Background: The off-screen context draws to the shared texture (typically attached to a local FBO).

  2. Insert a GPU Fence: Immediately after the draw call, insert a sync fence into the worker context:

    GLsync syncFence = glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE, 0);
glFlush(); // Ensure the command is sent to the GPU queue immediately

  3. Signal the Main Thread: Pass the GLsync handle and the shared texture ID to the main thread via a thread-safe message queue.

  4. Wait on the Display Thread: Before the visible context samples from the shared texture, instruct the GPU to wait for the fence to clear:

    glWaitSync(syncFence, 0, GL_TIMEOUT_IGNORED);

    glWaitSync causes the GPU’s server pipeline to wait for the background operations to complete before executing subsequent commands on the visible context, all without blocking the CPU thread.

  5. Clean Up: Once the texture is consumed, delete the sync object from either context:

    glDeleteSync(syncFence);

Resource Deletion Lifecycle

When deleting shared textures, OpenGL tracks references across all sharing contexts. If the off-screen context calls glDeleteTextures while the visible context has the texture bound or queued for drawing, the name is freed immediately, but the underlying GPU memory remains valid until all contexts unbind the texture.

To maintain predictable memory usage, establish clear ownership semantics: designate one context (usually the main display context) as the owner responsible for the final deletion of shared assets after synchronization guarantees that the background context has finished with them.

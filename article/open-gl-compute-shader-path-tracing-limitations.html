OpenGL Compute Shader Path Tracing Limitations

Implementing a path tracer using OpenGL compute shaders enables cross-platform, physically based rendering, but it introduces significant architectural bottlenecks that prevent it from matching modern ray tracing performance. This article outlines the core limitations governing this approach, focusing on the absence of fixed-function acceleration, memory access inefficiencies, compute unit occupancy constraints, and divergence issues inherent to general-purpose graphics processing unit (GPUT) programming within the legacy OpenGL pipeline.

1. Lack of Native Hardware Ray Tracing Acceleration

The single largest bottleneck is OpenGL’s inability to access dedicated ray tracing hardware, such as NVIDIA RT Cores or AMD Ray Accelerators. In modern APIs like Vulkan or DirectX 12, hardware units handle Bounding Volume Hierarchy (BVH) traversal and ray-triangle intersection tests autonomously. In an OpenGL compute shader, BVH traversal must be written entirely in software via Shader Storage Buffer Objects (SSBOs). Executing traversal logic through general-purpose arithmetic logic units (ALUs) consumes execution cycles that modern APIs bypass entirely.

2. Warp Divergence and Execution Serialization

GPUs execute threads in lockstep groups (warps of 32 threads on NVIDIA, wavefronts of 32 or 64 on AMD). Path tracing is inherently non-uniform:

  • Branch Divergence: Different rays hit different surfaces requiring different material evaluation logic (e.g., diffuse reflection versus complex dielectric refraction).
  • Loop Divergence: Secondary and shadow rays travel different distances through the BVH; some terminate immediately while others traverse deeply.

When threads within the same warp take different execution paths or loop for a different number of iterations, the GPU serializes execution, idling threads until the longest-running thread finishes its branch.

3. High Register Pressure and Low Occupancy

Traversing a BVH and calculating complex material physics in a single compute shader requires maintaining significant local state—such as current ray origins, directions, throughput, intersection data, and traversal stacks (even when using stackless traversal schemes like ropes or KD-trees). This demands a high number of registers per thread. As register usage spikes, the GPU hardware scheduler is forced to reduce the number of active warps per Streaming Multiprocessor (SM), drastically lowering occupancy and severely diminishing the GPU's ability to hide memory latency.

4. Incoherent Memory Access Patterns

Primary rays generated from a pinhole camera display strong spatial coherence, hitting adjacent scene geometry and sharing cache lines. However, once diffuse bounces occur, secondary rays scatter in pseudo-random directions. This destroys spatial and temporal cache locality in the L1 and L2 caches. Because the compute shader must continuously fetch BVH nodes, triangle indices, vertex positions, and texture maps from global memory across scattered memory addresses, the memory controllers become saturated with high-latency, uncoalesced memory reads.

5. Inflexible Thread Scheduling

Modern ray tracing pipelines offer mechanisms such as Shader Execution Reordering (SER) to regroup divergent rays on the fly according to their spatial or material coherence. OpenGL compute shaders offer no native dynamic re-scheduling capabilities. A work group dispatched via glDispatchCompute must retain its thread composition from start to finish, causing computational throughput to degrade significantly on deeper light bounces as the majority of threads terminate early while a minority continue to bounce.

How OpenGL Extensions Become ARB Approved

This article outlines the lifecycle of an OpenGL extension as it transitions from a proprietary, vendor-specific feature to an official Architecture Review Board (ARB) approved standard. You will learn about the tiers of the OpenGL extension hierarchy, the technical requirements for generalization, and the formal review and voting procedures conducted by the Khronos Group to ensure cross-vendor compatibility.

The OpenGL Extension Hierarchy

OpenGL uses a tiered naming system to indicate the maturity, portability, and consensus level of an extension:

  • Vendor-Specific (e.g., NV, AMD, INTEL): Developed by a single hardware manufacturer to expose proprietary hardware capabilities.
  • Multi-Vendor (EXT): Agreed upon and implemented by two or more hardware vendors, but not formally ratified as an official standard.
  • ARB Approved (ARB): Formally reviewed, standardized, and approved by the Khronos OpenGL Architecture Review Board. These represent features expected to be widely supported across compliant hardware.
  • Core Feature: An extension integrated directly into the baseline OpenGL specification, removing the need for extension-specific prefixes.

Step 1: Implementation as a Vendor or EXT Extension

The process begins when a hardware manufacturer introduces a new rendering technique or hardware capability. The vendor writes an initial specification and implements it under their vendor prefix (such as GL_NV_...).

Alternatively, if multiple hardware vendors identify a common need, they collaborate to write an EXT extension (such as GL_EXT_...). This stage serves as a live testing ground to evaluate software developer adoption, API ergonomics, and real-world performance without altering the core API.

Step 2: Demonstrating Demand and Portability

Before an extension can be considered for ARB status, it must prove that it is not tied to an isolated architectural quirk of a single GPU. The feature must demonstrate:

  • Widespread Developer Adoption: Substantial interest and use from software developers, game engines, or professional applications.
  • Hardware Generalizability: The ability to be implemented efficiently across multiple distinct GPU architectures from different vendors.

Step 3: ARB Working Group Proposal and Redrafting

A member of the Khronos Group formally proposes the feature to the OpenGL Working Group. During this phase, the technical specification undergoes significant revision:

  • Syntax Harmonization: Vendor-specific function and token names are changed to use the _ARB suffix (e.g., glFunctionARB).
  • Behavioral Normalization: Any implementation-specific shortcuts or proprietary constraints are generalized into vendor-neutral specifications.
  • Compatibility Interactions: The working group defines how the new functionality interacts with all existing OpenGL state machine rules, extensions, and core features.

Step 4: Review, Voting, and Publication

The Khronos OpenGL Working Group subjects the revised specification to peer review and formal debate. Members address edge cases, memory-management rules, and precision requirements.

Once the specification stabilizes, a formal ballot is held among voting members of the working group. If the vote passes, the extension receives official ARB ratification and is published in the Khronos OpenGL Extension Registry. Hardware vendors then update their drivers to expose the GL_ARB_ extension.

Step 5: Integration into Core OpenGL

While an ARB extension is officially standardized, it remains optional for hardware vendors to implement unless it is promoted to the core specification. During the preparation of a new baseline OpenGL version (such as OpenGL 4.5 or 4.6), the ARB reviews existing ARB extensions. Popular, stable, and essential ARB extensions have their ARB suffixes removed and are made mandatory requirements for any driver claiming compliance with that version of OpenGL.

glCompressedTexImage2D Texture Layout Requirements

This article provides a technical overview of the format layout requirements when uploading raw compressed textures to OpenGL using the glCompressedTexImage2D function. It details the structural alignment, memory packing, block-based sizing calculations, and driver expectations necessary to prevent hardware validation errors and ensure proper texture decompression on modern GPUs.

Block-Based Memory Structure

Unlike uncompressed texture uploads that operate on individual texels, glCompressedTexImage2D expects data organized into discrete, rectangular blocks of texels defined by the compression standard (such as S3TC/DXT, ETC2, or ASTC). Most common formats (BC1–BC7, ETC2) use fixed \(4 \times 4\) texel blocks, while ASTC supports variable dimensions from \(4 \times 4\) up to \(12 \times 12\).

The raw byte array passed to the data pointer must be a linear sequence of these encoded blocks. The blocks must be ordered in row-major order starting from the bottom-left of the image up to the top-right, adhering to OpenGL's standard texture coordinate origin \((0, 0)\).

Dimension Padding and Non-Power-of-Two Textures

If a texture's width or height is not an exact multiple of the compression block footprint (common at lower mipmap levels or with arbitrary non-power-of-two dimensions), the dimensions must be rounded up to the nearest whole block for memory allocation purposes:

  • Block Columns: \(\lceil \text{width} / \text{block\_width} \rceil\)
  • Block Rows: \(\lceil \text{height} / \text{block\_height} \rceil\)

Even if a mip level has nominal dimensions of \(2 \times 2\) or \(1 \times 1\), the underlying payload must provide the byte data for a complete \(4 \times 4\) block (or the appropriate ASTC block size). Passing partial block data will cause memory access violations or texture corruption.

Data Size Calculation (imageSize)

The imageSize parameter must explicitly match the total byte size of all required blocks. For standard formats:

  • BC1 (DXT1) / ETC2 RGB (8 bytes per \(4 \times 4\) block): \[\text{imageSize} = \max(1, \lfloor(\text{width} + 3) / 4\rfloor) \times \max(1, \lfloor(\text{height} + 3) / 4\rfloor) \times 8\]
  • BC3 (DXT5) / BC7 / ETC2 RGBA (16 bytes per \(4 \times 4\) block): \[\text{imageSize} = \max(1, \lfloor(\text{width} + 3) / 4\rfloor) \times \max(1, \lfloor(\text{height} + 3) / 4\rfloor) \times 16\]

If imageSize does not match the driver's calculated requirement for the specified internalformat, width, and height, the call will fail and trigger a GL_INVALID_VALUE error.

Pixel Storage Modes and Memory Packing

For compressed texture uploads, standard pixel unpack parameters like GL_UNPACK_ALIGNMENT, GL_UNPACK_ROW_LENGTH, and GL_UNPACK_SKIP_PIXELS are ignored by core OpenGL unless the GL_ARB_compressed_texture_pixel_storage extension is supported and enabled.

Consequently, the input buffer must be tightly packed:

  • No padding bytes are permitted between consecutive blocks in a row.
  • No padding bytes are permitted between consecutive rows of blocks.
  • Data must immediately follow in contiguous memory for the entire surface.

API Parameters Constraints

  • border: Must be set to 0. Any other value will generate a GL_INVALID_VALUE error, as borders are not supported on compressed textures.
  • internalformat: Must be an explicitly sized, hardware-supported compressed format constant (e.g., GL_COMPRESSED_RGBA_S3TC_DXT5_EXT, GL_COMPRESSED_RGB8_ETC2). Generic formats like GL_COMPRESSED_RGBA are invalid inputs for raw compressed uploads.

Desktop OpenGL Workgroup Size Limitations

When utilizing OpenGL compute shaders, local workgroup dimensions and total invocations are strictly governed by hardware-dependent limits exposed through the graphics driver. While the core OpenGL specification dictates minimum baseline requirements, physical graphics architectures and their corresponding desktop drivers—primarily from NVIDIA, AMD, and Intel—impose distinct constraints and performance implications. Understanding these limits is critical for ensuring cross-platform stability and preventing shader compilation or dispatch failures.

Specification Baselines vs. Hardware Limits

The OpenGL specification defines the minimum guaranteed limits that any compliant desktop driver (OpenGL 4.3 and above) must support. These values represent the floor; hardware vendors may exceed them, but portable code cannot assume availability beyond these minimums without runtime queries:

  • Maximum Invocations (GL_MAX_COMPUTE_WORK_GROUP_INVOCATIONS): The specification requires a minimum of 1024. This represents the absolute limit of the product of your local workgroup dimensions (\(X \times Y \times Z\)).
  • Maximum Workgroup Sizes (GL_MAX_COMPUTE_WORK_GROUP_SIZE): The specification minimums are 1024 for dimension \(X\), 1024 for dimension \(Y\), and 64 for dimension \(Z\).
  • Maximum Workgroup Count (GL_MAX_COMPUTE_WORK_GROUP_COUNT): The specification requires drivers to support at least 65,535 workgroups per dimension when calling glDispatchCompute.

A common pitfall is assuming that because individual dimension limits are 1024, a workgroup layout such as layout(local_size_x = 1024, local_size_y = 1024, local_size_z = 1) is valid. This configuration fails because the total invocation count (\(1024 \times 1024 = 1,048,576\)) vastly exceeds the maximum invocation limit of 1024.

Vendor-Specific Implementation Differences

While desktop drivers generally meet or exceed the OpenGL specification, their architectural implementations introduce distinct practical constraints:

NVIDIA

  • Dimension Limits: Typically matches the spec minimums: \(X = 1024\), \(Y = 1024\), \(Z = 64\).
  • Total Invocations: Fixed at 1024 across modern GeForce and RTX workstation drivers.
  • Dispatch Count: Often allows dimensions far exceeding the 65,535 minimum for dimension \(X\) (frequently up to \(2^{31} - 1\)), while dimensions \(Y\) and \(Z\) remain capped at 65,535.
  • Execution Granularity: NVIDIA hardware executes threads in warps of 32. Declaring workgroup sizes that are not multiples of 32 leads to underutilized execution units (warp divergence and idle threads).

AMD

  • Dimension Limits: Most modern AMD drivers report sizes of \(X = 1024\), \(Y = 1024\), and either 64 or 1024 for \(Z\), depending on the architecture generation.
  • Total Invocations: Remains at 1024 across almost all desktop Radeon drivers.
  • Dispatch Count: Similar to NVIDIA, AMD drivers often support larger dispatch counts on \(X\) (\(2^{31} - 1\)), while \(Y\) and \(Z\) often adhere to the 65,535 limit.
  • Execution Granularity: GCN and RDNA architectures utilize wavefronts of 64 or 32 threads. Aligning local workgroup sizes to multiples of 64 ensures full wave occupancy and avoids pipeline stalls across differing AMD driver revisions.

Intel

  • Dimension Limits: Intel integrated and discrete Arc graphics drivers typically report \(X = 1024\), \(Y = 1024\), and \(Z = 64\).
  • Total Invocations: Consistent with the specification minimum of 1024.
  • Dispatch Count: Intel drivers generally adhere to 65,535 across all three dimensions, though modern discrete Arc drivers allow higher bounds on the \(X\) axis.
  • Execution Granularity: Intel execution units (EUs) process subgroups natively sized between 8, 16, or 32 threads depending on compilation heuristics and register pressure.

Dynamic Workgroup Validation

To ensure code runs reliably across all desktop environments, limits must be validated dynamically at runtime using OpenGL queries rather than hardcoded assumptions:

// Query maximum invocation limit (X * Y * Z)
GLint maxInvocations;
glGetIntegerv(GL_MAX_COMPUTE_WORK_GROUP_INVOCATIONS, &maxInvocations);

// Query maximum size per dimension
GLint maxSizes[3];
glGetIntegeri_v(GL_MAX_COMPUTE_WORK_GROUP_SIZE, 0, &maxSizes[0]); // X
glGetIntegeri_v(GL_MAX_COMPUTE_WORK_GROUP_SIZE, 1, &maxSizes[1]); // Y
glGetIntegeri_v(GL_MAX_COMPUTE_WORK_GROUP_SIZE, 2, &maxSizes[2]); // Z

// Query maximum global dispatch counts
GLint maxCounts[3];
glGetIntegeri_v(GL_MAX_COMPUTE_WORK_GROUP_COUNT, 0, &maxCounts[0]); // X
glGetIntegeri_v(GL_MAX_COMPUTE_WORK_GROUP_COUNT, 1, &maxCounts[1]); // Y
glGetIntegeri_v(GL_MAX_COMPUTE_WORK_GROUP_COUNT, 2, &maxCounts[2]); // Z

Shared Memory Constraints

In addition to pure dimension counts, workgroup sizing is indirectly limited by shared memory (GL_MAX_COMPUTE_SHARED_MEMORY_SIZE). The OpenGL baseline guarantees 32 KB per workgroup, though modern desktop drivers from NVIDIA and AMD frequently support 48 KB, 64 KB, or more. If a shader utilizes significant shared memory, the driver may fail to dispatch large workgroups due to insufficient on-chip cache resources, even if the workgroup dimensions conform to the invocation limits.

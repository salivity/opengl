Legacy OpenGL Auxiliary Buffers in Early Workstations

This article provides a technical overview of the legacy auxiliary color buffers implemented in early workstation OpenGL hardware. It examines how systems allocated and addressed these buffers, the specific hardware environments that supported them, their primary use cases for off-screen computation and multi-pass effects, and their eventual replacement by modern rendering techniques such as Framebuffer Objects (FBOs).

The Architecture of Auxiliary Buffers

In the original OpenGL specifications (OpenGL 1.0 through 1.5), the default framebuffer provided by the operating system’s windowing system could include more than just standard display buffers. Beyond the front and back buffers for double buffering, and left and right buffers for stereoscopic rendering, the specification allowed for non-displayable scratchpad color buffers designated as auxiliary buffers: GL_AUX0, GL_AUX1, GL_AUX2, and GL_AUX3.

Applications queried hardware support using glGetIntegerv(GL_AUX_BUFFERS, &count). While the OpenGL specification supported an implementation-dependent count of auxiliary buffers (typically up to four), consumer-grade hardware rarely implemented any due to memory constraints. High-end Unix workstations, however, routinely exposed one to four of these 24-bit or 32-bit color planes directly within video memory.

Target Hardware Implementations

Auxiliary buffers were primarily found on specialized professional graphics systems throughout the 1990s and early 2000s, including:

  • Silicon Graphics (SGI): Workstations based on the IRIX operating system, such as the SGI Indigo2, Octane, and Onyx systems equipped with RealityEngine, InfiniteReality, or Impact graphics subsystems.
  • Sun Microsystems and HP Workstations: Systems equipped with Elite3D, Creator3D, or Visualize FX graphics hardware.
  • Professional PC Workstation Cards: Early workstation-class accelerators such as the 3Dlabs Wildcat series and early Evans & Sutherland boards.

In these systems, video memory (VRAM) was statically allocated when configuring the visual or pixel format via GLX or WGL. If an application requested a visual with auxiliary buffers, the system dedicated physical video memory to those buffers for the lifetime of that context.

Operational Usage

Developers directed drawing operations to these buffers using glDrawBuffer() and read operations using glReadBuffer(). Common workflows included:

  • Multi-Pass Compositing: An application could render geometry into GL_AUX0, compute a secondary pass into GL_AUX1, and combine both passes into GL_BACK using pixel-transfer operations or hardware blending.
  • Object Picking and Selection: Developers rendered unique object identifiers (encoded as RGB colors) into an auxiliary buffer. When the user clicked the mouse, glReadPixels() sampled the coordinate directly from the auxiliary buffer without interrupting the visible scene on the front or back buffers.
  • Intermediate Texture Generation: Early hardware lacked the ability to render directly to textures. Auxiliary buffers served as off-screen staging grounds from which pixels were transferred to texture memory via glCopyTexImage2D() or glCopyTexSubImage2D().

Obsolescence and Removal

Auxiliary buffers suffered from fundamental limitations: they were tied to the windowing system, shared the fixed resolution and bit-depth of the visible window, and wasted substantial VRAM if not actively used.

The industry initially addressed these limitations with hardware-accelerated off-screen rendering contexts known as pbuffers (WGL_ARB_pbuffer and GLX_SGIX_pbuffer). Auxiliary buffers became entirely obsolete with the introduction of the Framebuffer Object extension (GL_EXT_framebuffer_object), later integrated into the core specification. Modern Multiple Render Target (MRT) pipelines allow dynamic binding of off-screen textures directly as color attachments (GL_COLOR_ATTACHMENT0 through GL_COLOR_ATTACHMENTn), leading to the complete deprecation and removal of GL_AUXn in OpenGL Core Profiles.

Synchronizing Compute Shaders with Vertex Pullers in OpenGL

In modern OpenGL, compute shaders frequently generate or modify geometry data directly on the GPU, requiring explicit synchronization before that data can be safely consumed by the fixed-function vertex puller. Because compute shader writes bypass traditional pipeline stages via incoherent memory access, developers must insert a memory barrier using glMemoryBarrier with the GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT flag. This ensures all pending memory writes to buffer objects are fully flushed, visible, and coherent before the vertex fetching hardware initiates subsequent draw commands, effectively eliminating read-after-write hazards.

The Memory Coherency Problem

Compute shaders typically write vertex data into Shader Storage Buffer Objects (SSBOs). In modern graphics pipelines, this data is cached in L1/L2 caches that are not automatically coherent with the specialized cache hierarchies utilized by the fixed-function vertex fetch hardware (the vertex puller).

If a draw call such as glDrawArrays or glDrawElements is dispatched immediately after a compute dispatch without synchronization, a read-after-write (RAW) hazard occurs. The vertex puller may read stale, partially written, or out-of-order data, leading to flickering, missing primitives, or GPU memory faults.

Using glMemoryBarrier

To resolve this hazard, OpenGL provides the glMemoryBarrier(GLbitfield barriers) API. This command forces memory transactions issued before the barrier to complete and become visible to subsequent commands that access memory through the specified pipeline stages.

To synchronize compute shader writes with the vertex attribute fetch stage:

glMemoryBarrier(GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT);

The GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT guarantees that any memory stores initiated prior to the barrier (such as image stores or SSBO writes) are reflected in data read by the vertex puller via vertex attribute arrays (glVertexAttribPointer or glVertexArrayVertexBuffer).

Handling Element and Draw Indirect Buffers

If the compute shader generates indices or indirect drawing parameters in addition to vertex attributes, additional barrier bits must be combined with a bitwise OR:

  • Index Buffers: If generating or modifying indices consumed by glDrawElements, include GL_ELEMENT_ARRAY_BARRIER_BIT.
  • Indirect Draw Arguments: If populating draw command arguments for glDrawArraysIndirect or glDrawElementsIndirect, include GL_COMMAND_BARRIER_BIT.
// Example: Synchronizing attributes, indices, and indirect draw buffers
glMemoryBarrier(GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT | 
                GL_ELEMENT_ARRAY_BARRIER_BIT | 
                GL_COMMAND_BARRIER_BIT);

Complete Synchronization Workflow

A standard procedural generation or GPU-culling loop follows these discrete steps:

  1. Bind Resources: Bind the target buffer as an SSBO (GL_SHADER_STORAGE_BUFFER) for the compute pass.
  2. Execute Compute: Dispatch the compute shader using glDispatchCompute(numGroupsX, numGroupsY, numGroupsZ).
  3. Insert the Barrier: Invoke glMemoryBarrier(GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT) immediately after the dispatch.
  4. Bind Vertex Arrays: Bind the Vertex Array Object (VAO) that references the modified buffer as a GL_ARRAY_BUFFER.
  5. Issue Draw Call: Execute glDrawArrays or glDrawElements. The vertex puller is guaranteed to read the final, coherent data produced by the compute shader.

Optimization and Ordering

A common mistake is placing the memory barrier immediately before the draw call instead of directly after the compute dispatch, or vice versa, without considering intervening CPU-side operations. The barrier only dictates order between commands issued before it and commands issued after it in the OpenGL command stream. Placing the barrier immediately prior to the draw call allows other non-dependent GPU work to overlap with compute execution, maximizing pipeline utilization while maintaining correctness.

CUDA OpenGL Interop Synchronization Rules

Sharing data between NVIDIA CUDA engines and OpenGL enables high-performance computing and real-time visualization without costly CPU-side memory transfers. However, because CUDA and OpenGL maintain separate command queues and execution contexts, strict synchronization rules must be observed to prevent data races, screen tearing, and graphics pipeline stalls. This article details the core synchronization mechanisms governing CUDA-to-OpenGL interoperability, covering resource states, legacy map/unmap semantics, and modern semaphore-driven synchronization.

Resource Registration and Mapping Lifecycle

When using the CUDA Graphics Interoperability API (cudaGraphicsGLRegisterBuffer, cudaGraphicsGLRegisterImage), the graphics resource follows a strict state machine:

  1. Registered State: The OpenGL buffer (such as a Pixel Buffer Object or Vertex Buffer Object) or texture is registered with CUDA. This is an expensive operation and must be performed once during initialization, not per frame.
  2. Mapped State: CUDA requests exclusive access via cudaGraphicsMapResources(). While mapped, OpenGL must not attempt to read, write, or bind the underlying resource. Doing so results in undefined behavior or pipeline corruption.
  3. Unmapped State: CUDA yields access back to OpenGL via cudaGraphicsUnmapResources(). Once unmapped, the resource is safe for OpenGL to bind and draw. CUDA kernels must not access the device pointers obtained during the mapped state.

Legacy Synchronization via Map and Unmap

In the standard interoperability model, synchronization is tied directly to the mapping calls:

  • Implicit Stream Synchronization: When cudaGraphicsMapResources(count, resources, stream) is invoked, CUDA inserts an implicit wait on the specified CUDA stream. The CUDA stream will not execute subsequent kernels until all prior OpenGL commands affecting those resources have fully completed.
  • Unmapping and OpenGL Resumption: Calling cudaGraphicsUnmapResources(count, resources, stream) enqueues an unmap operation into the CUDA stream. However, to guarantee that OpenGL does not render stale data, the application must ensure the unmap operation has finished before issuing rendering commands. This is typically achieved by synchronizing the CUDA stream (cudaStreamSynchronize) or using OpenGL sync objects (fences).

While straightforward, frequent map and unmap calls introduce CPU-side driver overhead and can serialize the GPU pipeline.

Modern Explicit Synchronization via External Semaphores

Modern high-performance pipelines bypass frequent mapping by using the EXT_external_objects OpenGL extension paired with CUDA External Resource Interoperability (cudaImportExternalMemory, cudaImportExternalSemaphore). Under this paradigm, resources remain permanently mapped, and execution ordering is enforced through GPU-side semaphores:

  1. OpenGL-to-CUDA Transition:
    • OpenGL finishes rendering or reading the buffer.
    • OpenGL signals a semaphore using glSignalSemaphoreEXT().
    • CUDA waits on this semaphore inside a specific stream using cudaWaitExternalSemaphoresAsync(). CUDA execution halts in that stream until OpenGL reaches the signal point.
  2. CUDA-to-OpenGL Transition:
    • The CUDA engine executes its compute kernels on the shared memory.
    • CUDA signals a second external semaphore upon completion using cudaSignalExternalSemaphoresAsync().
    • OpenGL calls glWaitSemaphoreEXT() on its context before issuing draw calls that sample or read the shared data.

This approach executes purely on the GPU timeline without CPU blocking, maintaining maximum throughput and preventing pipeline bubbles.

Essential Synchronization Rules Summary

  • Mutual Exclusion: Never issue OpenGL draw or read commands on an interop resource while a CUDA kernel is actively reading or writing to it.
  • Stream Association: Always bind interop mapping or semaphore operations to a dedicated cudaStream_t rather than the default (null) stream to avoid accidental serialization of the entire CUDA context.
  • Context Consistency: The OpenGL context owning the shared resource must be current on the host thread when calling registration, mapping, and unmapping functions.
  • Flushing Requirements: If synchronizing via CPU-side primitives rather than external semaphores, call glFlush() after OpenGL operations to ensure commands are dispatched to the GPU before CUDA waits on them.

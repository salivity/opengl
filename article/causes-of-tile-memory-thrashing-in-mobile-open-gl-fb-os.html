Causes of Tile Memory Thrashing in Mobile OpenGL FBOs

In mobile OpenGL development, heavy reliance on Framebuffer Objects (FBOs) often leads to a severe performance bottleneck known as tile memory thrashing. Because mobile graphics processors rely on Tile-Based Deferred Rendering (TBDR) architectures, switching between multiple FBOs or mismanaging render targets forces the GPU to constantly flush and reload pixel data between fast on-chip tile memory and slow system RAM. Understanding how TBDR functions and identifying the specific operations that trigger these redundant memory transactions is essential for maintaining high frame rates and thermal efficiency on mobile devices.

Understanding the TBDR Architecture

Unlike desktop GPUs that typically use Immediate Mode Rendering (IMR), mobile GPUs—such as ARM Mali, Qualcomm Adreno, and Imagination PowerVR—employ Tile-Based (Deferred) Rendering architectures.

A TBDR GPU divides the render screen into small grids called tiles (commonly 16x16 or 32x32 pixels). It processes geometry first, assigns primitives to the corresponding tiles, and then shades one tile at a time entirely within small, high-speed, on-chip SRAM cache. Once shading for that tile is finished, the completed pixel data is resolved and written out to main system memory (DRAM).

Tile memory thrashing occurs when the GPU cannot complete its work within this on-chip cache and is forced to repeatedly evict and reload tile data across the memory bus.

Primary Causes of Tile Memory Thrashing

1. Frequent FBO Switching (Ping-Ponging)

Every time glBindFramebuffer() is called to activate a different FBO, the mobile driver must close the current rendering pass. The contents of the on-chip tile memory must be written back to external DRAM, and the next FBO's attachments must be loaded from DRAM into tile memory. Alternating between multiple FBOs within a single frame—such as repeatedly swapping textures for blur passes or multi-step post-processing—multiplies these high-cost memory transfers.

2. Missing Clear or Invalidate Directives

When switching to an FBO, the GPU needs to know whether the existing contents in system memory matter.

  • Unnecessary Loads: If an FBO is bound without immediately calling glClear() or passing GL_DONT_CARE (via extensions or subpasses), the GPU assumes the previous content must be preserved and loads the full texture from DRAM into tile memory before rendering.
  • Unnecessary Stores: If depth, stencil, or auxiliary color attachments are not discarded at the end of a render pass using glInvalidateFramebuffer(), the GPU wastes memory bandwidth writing intermediate data back to system memory that will never be displayed.

3. Intermediate Sampling (Read-After-Write Hazards)

Attempting to sample a texture that was just written to by an active FBO creates a pipeline dependency. If the texture is not fully resolved, the GPU must flush its current tile pipelines, wait for the writes to complete to DRAM, and then read the texture back through the texture cache. This stalls the pipeline and breaks the hardware's tile-pipelining optimizations.

4. Oversized Attachments and Multiple Render Targets (MRT)

On-chip tile memory has a strict physical capacity (often just a few kilobytes per tile). Using high-precision buffers (e.g., 32-bit floating-point textures), extensive Multiple Render Targets (MRT) for deferred shading, or high-sample multisample anti-aliasing (MSAA) can exceed this physical limit. When attachments exceed the tile buffer capacity, the hardware may be forced to split rendering passes or spill intermediate samples into external memory.

Mitigation Strategies

  • Batch by Render Target: Group all drawing commands associated with a specific FBO together to minimize switching.
  • Explicit Clears and Discards: Always clear attachments at the start of a pass with glClear(), and explicitly invalidate temporary attachments (like depth and stencil buffers) with glInvalidateFramebuffer() before unbinding.
  • Leverage Native On-Chip Extensions: Use features like GL_EXT_shader_pixel_local_storage or subpasses in modern APIs (Vulkan) to perform multi-pass computations directly within on-chip memory without flushing to DRAM.
  • Downscale Intermediate Targets: Use the lowest acceptable resolution and bit depth for off-screen buffers to minimize the volume of data transferred when flushes do occur.

How local_size_x Impacts GPU Occupancy in OpenGL

In OpenGL compute shaders, the layout(local_size_x, ...) qualifier defines the dimensions of a workgroup, directly dictating how the GPU schedules threads, allocates hardware resources, and saturates compute units. Choosing the correct workgroup size balances register usage, shared memory consumption, and thread scheduling to maximize GPU occupancy—the ratio of active execution units to the hardware's theoretical maximum. Setting this value incorrectly can lead to severe hardware underutilization or resource starvation.

Hardware Execution Units: Warps and Wavefronts

GPUs do not execute individual threads in isolation. Instead, they bundle threads into lockstep execution units known as warps on NVIDIA hardware (typically 32 threads) or wavefronts on AMD hardware (typically 32 or 64 threads).

When specifying layout(local_size_x = N), the total number of invocations in the workgroup should ideally be an integer multiple of the native warp or wavefront size. If you specify an unaligned size—such as layout(local_size_x = 40) on an architecture using 32-thread warps—the GPU must allocate two full warps (64 thread slots) to service the group. In this scenario, 24 thread slots remain completely idle, directly degrading hardware efficiency and compute throughput.

The Occupancy Trade-Off

Occupancy measures how effectively the hardware scheduler can hide latency. GPUs hide instruction and memory latency by rapidly switching between active warps on a Streaming Multiprocessor (SM) or Compute Unit (CU). If one warp stalls waiting for a texture fetch or buffer load, the scheduler dispatches instructions from another warp.

Workgroup size affects occupancy through three primary hardware limits per compute unit:

  1. Maximum Threads per Multiprocessor: Hardware limits total active threads (often 1024 to 2048 per SM/CU).
  2. Maximum Workgroups per Multiprocessor: Hardware caps the number of concurrent workgroups an execution unit can track (typically 16 to 32).
  3. Register and Shared Memory Limits: Each thread requires general-purpose registers, and each workgroup consumes a slice of local shared memory (shared memory qualifiers).

The Impact of Small Workgroups

Setting local_size_x to a very small number (such as 16, 32, or 64) risks running into the maximum workgroup limit before filling the execution unit's thread capacity. For instance, if an SM has a limit of 16 concurrent workgroups and a capacity of 2048 threads, choosing local_size_x = 32 caps the SM at only 512 active threads (16 × 32). This caps occupancy at 25%, drastically reducing the scheduler's ability to hide memory stalls.

The Impact of Large Workgroups

Conversely, setting local_size_x too high (such as 512 or 1024) coarsens scheduling granularity. A multiprocessor must have enough free registers and shared memory to house the entire workgroup before launching it. If a shader has high register pressure, an SM might only have enough resources to host a single 1024-thread workgroup. If that workgroup blocks on a synchronization barrier (barrier()), the entire multiprocessor stalls, with no alternative workgroups available to execute.

Practical Guidelines for OpenGL Shaders

For most modern architectures, workgroup sizes between 64 and 256 invocations provide the most stable occupancy profiles:

  • 128 or 256 threads: Typically optimal for general compute tasks, as these sizes divide evenly into the scheduling capacities of modern NVIDIA, AMD, and Intel architectures.
  • Shared Memory Usage: Always calculate shared memory per workgroup. If an SM provides 64 KB of shared memory and your workgroup uses 33 KB, only one workgroup can run on that SM at a time, cutting occupancy in half regardless of thread count.
  • Latency vs. Occupancy: Achieving 100% occupancy is not always required for peak performance. A shader with high instruction-level parallelism (ILP) or primarily arithmetic workloads can reach peak throughput at moderate occupancy (50–70%), whereas memory-bound compute shaders rely heavily on high occupancy to hide latency.

OpenGL Atomic Operations on Buffer Data Guarantees

This article examines the guarantees provided by modern OpenGL when performing atomic memory operations on raw buffer data, such as Shader Storage Buffer Objects (SSBOs) and Atomic Counter Buffers. It details the core mechanisms of hardware-level atomicity, memory visibility, ordering semantics, and alignment constraints that govern concurrent read-modify-write operations across parallel shader invocations.

Hardware Atomicity

When executing atomic functions (such as atomicAdd, atomicMin, atomicExchange, or atomicCompSwap) in GLSL on buffer variables, OpenGL guarantees that the read-modify-write sequence is indivisible. If multiple shader invocations target the exact same 32-bit (or 64-bit, where supported) memory location concurrently, the hardware serializes these transactions. No invocation will read a partially updated state, and no updates will be silently dropped due to data races between concurrent atomic operations.

Memory Coherency and Qualifiers

OpenGL employs a weakly ordered memory model. By default, shader invocations may cache memory reads and writes, meaning that updates made by one invocation are not automatically visible to others.

To ensure correct access to raw buffer data:

  • The coherent Qualifier: Buffer variables subjected to atomic operations across multiple invocations should be declared with the coherent memory qualifier in GLSL. This instructs the compiler and hardware that the variable is shared across invocations and bypasses local caching mechanisms that would otherwise lead to stale data.
  • Non-Atomic Access Hazards: Atomicity guarantees apply strictly to concurrent operations where all participating invocations use atomic functions. If one invocation executes an atomic write while another performs a normal assignment or read to the same address, race conditions occur, and the behavior is undefined.

Visibility and Memory Barriers

Atomicity does not imply global execution ordering or automatic cross-stage visibility. OpenGL provides two levels of barriers to guarantee visibility:

  1. Intra-Stage Barriers (GLSL): Within compute shaders, calling memoryBarrierBuffer() or memoryBarrierShared() guarantees that writes performed before the barrier are committed and visible to subsequent operations within the same workgroup (when paired with barrier()).
  2. Inter-Stage Barriers (OpenGL API): Updates performed via atomic buffer operations are not automatically visible to subsequent pipeline stages or draw calls. The application must invoke glMemoryBarrier(GL_SHADER_STORAGE_BARRIER_BIT) (or the appropriate bitmask for the target resource) to guarantee that all atomic writes complete and are flushed before subsequent commands read the updated buffer data.

Execution Ordering Guarantees

While individual atomic operations are serialized, the order of execution among concurrent invocations is non-deterministic. OpenGL provides no guarantees regarding which invocation will execute its atomic operation first. If strict sequential ordering is required, the algorithm must implement custom synchronization structures, such as spinlocks or pass-based scheduling, using operations like atomicCompSwap.

Data Alignment and Type Restrictions

OpenGL guarantees atomic behavior only on naturally aligned memory:

  • Standard atomic operations are guaranteed on 32-bit signed and unsigned integers (int, uint).
  • 64-bit integer atomics are supported only when the GL_ARB_gpu_shader_int64 or GL_NV_shader_atomic_int64 extensions are present.
  • The memory address accessed by an atomic function must be aligned to the size of the operand (e.g., 4-byte boundaries for 32-bit atomics). Performing atomic operations on unaligned data results in undefined behavior or hardware exceptions.

Host-Device Synchronization

Modifications made to raw buffer data via GPU atomics are not coherent with CPU host memory by default. If the buffer is mapped into client memory, visibility requires proper synchronization through sync objects (glFenceSync, glClientWaitSync) and buffer mapping flags (such as GL_MAP_COHERENT_BIT or explicit flushes via glFlushMappedBufferRange).

OpenGL Compute Shaders for Voxel Fluid Simulation

Modern real-time fluid simulations depend on spatial acceleration structures, such as uniform voxel grids, to efficiently resolve neighboring particle interactions in Lagrangian Smoothed Particle Hydrodynamics (SPH) or to store physical quantities in Eulerian grid systems. OpenGL compute shaders execute this spatial discretization entirely on the GPU by mapping continuous particle coordinates into 3D voxel indices and committing that data to video memory using Shader Storage Buffer Objects (SSBOs) or 3D texture images. This article explores the core mechanisms, memory architectures, and atomic writing routines used by compute shaders to construct and populate spatial acceleration grids for fluid dynamics.

Coordinate Discretization and Grid Indexing

Before writing spatial data, a compute shader must discretize continuous world-space particle positions into uniform voxel coordinates. Given a simulation bounding box origin and a uniform cell size corresponding to the fluid smoothing radius, the compute shader calculates the discrete 3D cell index for each particle:

ivec3 cellCoords = ivec3(floor((particlePos - gridOrigin) / cellSize));

To store this information within a contiguous memory block, the 3D cell coordinate is converted into a 1D linear array index:

uint cellIndex = cellCoords.x + cellCoords.y * gridResolution.x + cellCoords.z * (gridResolution.x * gridResolution.y);

Boundary clamping or spatial hashing using modulo arithmetic is applied to handle particles that drift near or outside the active grid bounds.

Target Memory Formats in OpenGL

OpenGL provides two primary mechanisms for compute shaders to write spatial grid data:

  1. Shader Storage Buffer Objects (SSBOs): SSBOs offer arbitrary, read-write array storage defined through the std430 layout. They are the standard choice for sparse voxel grids, particle index lists, and atomic head-pointer structures because they allow unstructured, dynamically sized memory access.
  2. 3D Textures via Image Load/Store: For dense, Eulerian fluid simulation grids (such as MAC grids storing velocity, pressure, and density fields), compute shaders bind a 3D texture using glBindImageTexture and write voxel data directly via the imageStore() function.

Strategies for Writing Spatial Data

Because hundreds of thousands of fluid particles process simultaneously across GPU workgroups, multiple threads will attempt to write to the same voxel cell concurrently. Compute shaders use one of two primary strategies to resolve these race conditions:

1. Atomic Linked Lists (Head-Pointer Approach)

In this approach, two SSBOs are allocated: a HeadPointers buffer sized to the total number of grid cells and a ParticleLinkedList buffer sized to the total number of particles.

  • The HeadPointers buffer is initially cleared to -1 (indicating an empty cell).
  • Each compute invocation represents a particle. After calculating its cellIndex, the shader uses atomicExchange() to swap the existing head pointer with its own particle ID:
layout(std430, binding = 0) buffer HeadBuffer {
    int cellHead[];
};

layout(std430, binding = 1) buffer ListBuffer {
    int nextParticleIndex[];
};

void insertParticle(uint particleID, uint cellIndex) {
    int previousHead = atomicExchange(cellHead[cellIndex], int(particleID));
    nextParticleIndex[particleID] = previousHead;
}

This constructs a reverse linked list for every voxel cell without requiring a sorting pass.

2. Bin Counting and Prefix Sum (Sorted Cell Buckets)

For improved cache coherency during subsequent neighbor-search passes, compute shaders can sort particles into contiguous cell buckets using atomic counting:

  1. Count Pass: Each compute thread increments the cell counter using atomicAdd(cellCounts[cellIndex], 1).
  2. Prefix Sum (Scan) Pass: A parallel prefix sum computes cell offsets, turning raw counts into starting memory offsets for every voxel.
  3. Scatter Pass: The shader writes particle indices into an ordered particle array at their resolved offset using a secondary local index offset counter.

3. Eulerian Grid Splatting

When simulating grid-based fluids, properties such as mass, velocity, or marker values are transferred (splatted) from particles to surrounding voxel nodes using interpolation kernels. Compute shaders write accumulated values into float-based SSBOs using atomicAdd (often using integer-scaled fixed-point conversion if hardware lacks native floating-point atomics) or by sampling neighboring particles through a gather pass targeting 3D image textures via imageStore().

Synchronization and Memory Barriers

Unsynchronized reads and writes across shader invocations cause race conditions and pipeline stalls. To maintain memory coherence between compute passes, explicit barriers are required:

  • Inside the Shader: When workgroup threads share local voxel memory (shared), barrier() synchronizes execution, while memoryBarrierShared() or memoryBarrierBuffer() guarantees that previous writes are visible to other threads in the workgroup.
  • On the Host (OpenGL API): Between compute dispatches (such as between the grid allocation pass and the neighbor evaluation pass), the application must issue driver-level barriers:
glDispatchCompute(numWorkgroups, 1, 1);
glMemoryBarrier(GL_SHADER_STORAGE_BARRIER_BIT | GL_TEXTURE_FETCH_BARRIER_BIT);

This enforces that all voxel writes initiated by the compute shader are fully committed to memory before subsequent compute or render pipelines read the spatial acceleration structure.

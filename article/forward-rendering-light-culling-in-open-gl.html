Forward+ Rendering Light Culling in OpenGL

Forward+ rendering optimizes the traditional forward rendering pipeline by decoupling light evaluation from geometric complexity through a screen-space tile-culling phase. This article details how OpenGL compute shaders are leveraged to perform light tile assignment, covering the partitioning of the screen into discrete tiles, the calculation of tile-specific frustums, the parallel intersection testing of light volumes against those frustums, and the storage of per-tile light indices in Shader Storage Buffer Objects (SSBOs) for the final shading pass.

The Forward+ Pipeline Context

Traditional forward rendering forces every fragment to test against every active light in the scene, scaling poorly at \(O(\text{geometry} \times \text{lights})\). Forward+ introduces a three-phase pipeline to resolve this:

  1. Depth Pre-pass: Renders the scene's geometry to generate a depth buffer.
  2. Light Culling (Compute Shader): Uses the depth buffer to determine which lights affect specific screen-space tiles and assigns those lights to tile-specific lists.
  3. Forward Shading Pass: Standard forward rendering, but fragments only calculate lighting from the lights assigned to their specific screen tile.

Tile Division and Compute Workgroup Mapping

The screen is divided into a uniform two-dimensional grid of tiles, commonly sized at \(16 \times 16\) pixels. In OpenGL, an execution of a compute shader is dispatched to process this grid:

// In GLSL Compute Shader
layout(local_size_x = 16, local_size_y = 16, local_size_z = 1) in;

Each workgroup corresponds to a single tile. The built-in variable gl_WorkGroupID.xy identifies the coordinate of the tile on screen, while gl_LocalInvocationIndex (ranging from 0 to 255) identifies the specific thread within that workgroup.

Depth Reduction and Frustum Generation

To cull lights accurately along the Z-axis, the compute shader must know the minimum and maximum depth within each tile.

  1. Each thread samples the depth texture at its corresponding pixel coordinate using texelFetch.
  2. The depths are linearized and converted into view space.
  3. The workgroup uses parallel reduction (or atomic operations using shared memory) to calculate the tile’s absolute minimum and maximum depth values.
  4. Using the four corner coordinates of the screen-space tile combined with the tile’s min/max depth bounds, the shader constructs six view-space planes that define the tile's bounding frustum.

Parallel Light Culling

Once the tile's frustum is defined, all lights in the scene are tested against it. Because scenes can contain thousands of lights, the compute shader distributes this work evenly among the 256 threads in the workgroup.

  • Lights are stored linearly in a global Shader Storage Buffer Object (SSBO) containing positions, radii, and colors.
  • Threads iterate through the global light buffer in parallel strides. For example, thread 0 tests light 0, thread 1 tests light 1, up to light 255, looping until all scene lights are evaluated.
  • The intersection test evaluates whether a light's bounding volume (typically a sphere for point lights) intersects the six planes of the tile frustum. A point light is within the tile if the signed distance from its center to any of the six planes is greater than the negative radius of the light.

Shared Memory and Light Index Accumulation

To avoid expensive global memory writes during intersection testing, threads write to fast on-chip shared memory:

shared uint tileLightCount;
shared uint tileLightIndices[MAX_LIGHTS_PER_TILE];

  1. At the beginning of the shader, tileLightCount is initialized to zero by a single thread (gl_LocalInvocationIndex == 0), followed by a barrier() to synchronize the workgroup.

  2. When a thread confirms a light intersects the tile frustum, it atomically increments the shared counter:

    uint slot = atomicAdd(tileLightCount, 1);
if (slot < MAX_LIGHTS_PER_TILE) {
    tileLightIndices[slot] = lightIndex;
}

  3. A second barrier() ensures all threads have finished testing and writing before moving forward.

Writing to Global Buffers

Once all lights have been culled, the compute shader flushes the shared memory data into global SSBOs visible to subsequent render passes. This generally uses a contiguous light index list paired with a grid buffer:

  • Light Grid Buffer: A 2D buffer mapping each tile coordinate to an offset and a count in the global index array.
  • Global Light Index List: A flat buffer storing the packed light IDs.

A single thread in the workgroup fetches a global offset using a global atomic counter, updates the light grid entry for the current tile, and copies the light indices from tileLightIndices into the global light index list.

Consumption in the Fragment Shader

In the final forward shading pass, fragments determine their screen-space tile using gl_FragCoord.xy / 16.0. The fragment shader reads the tile’s offset and count from the Light Grid Buffer SSBO, iterates strictly over the light indices stored for that specific tile in the Global Light Index List, and applies standard lighting equations. This restricts light evaluation to only the lights that realistically contribute to that fragment.

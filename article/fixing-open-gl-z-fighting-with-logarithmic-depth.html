Fixing OpenGL Z-Fighting with Logarithmic Depth

Rendering massive virtual worlds such as space simulators, planetary terrain, and expansive open-world games often leads to z-fighting due to standard depth buffer limitations. Logarithmic depth buffering solves this problem by redistributing floating-point precision evenly across the camera's viewing frustum using a logarithmic curve. By allocating depth precision proportionally to absolute distance, it eliminates surface flickering across enormous depth ranges—from millimeters to astronomical units—without requiring multiple rendering passes or extreme near-plane clipping.

The Precision Issue with Standard Perspective Depth

In standard OpenGL perspective projections, depth values undergo a perspective divide that maps view-space coordinates to normalized device coordinates (NDC). The resulting depth value in the hardware depth buffer is inversely proportional to the camera distance (\(1/z\)).

Because of this reciprocal relationship, the vast majority of depth buffer precision is allocated within a tiny fraction of the view volume immediately adjacent to the near clipping plane. For example, in a scene with a near plane of \(0.1\) units and a far plane of \(10,000\) units, roughly half of all available depth values are consumed within the first few units of the camera. When rendering objects thousands or millions of units away, the available bits cannot differentiate between surfaces that are meters apart, resulting in identical depth values and severe visual flickering (z-fighting).

How Logarithmic Depth Rebalances Precision

A logarithmic depth buffer replaces the hyperbolic \(1/z\) distribution with a logarithmic mapping. Instead of concentrating precision near the camera, the precision scales relative to the distance of the geometry:

\[\text{Depth} \propto \log(C \cdot z + 1)\]

Where \(z\) is the view-space depth and \(C\) is a constant that adjusts the distribution curve.

Under a logarithmic distribution, precision decreases at a controlled geometric rate rather than collapsing immediately after the near plane. A surface separation of 1 millimeter at a distance of 1 meter requires the same relative precision as a 1-kilometer separation at 1,000 kilometers. By aligning depth resolution with human perception and geometric scale, the system avoids z-buffer underflows over astronomical distances.

Implementation in Modern OpenGL

In modern OpenGL, a logarithmic depth buffer can be implemented directly within GLSL shaders. The transformation can be handled in either the vertex shader or the fragment shader.

Fragment Shader Approach

The most accurate method computes the logarithmic depth per-fragment and writes directly to gl_FragDepth. This prevents interpolation artifacts along the edges of large polygons:

// Fragment Shader
in float v_viewDepth;
uniform float u_farPlane;
const float C = 1.0;

void main() {
    // Standard lighting and texturing calculations...

    // Calculate logarithmic depth
    float logDepth = log(C * v_viewDepth + 1.0) / log(C * u_farPlane + 1.0);
    gl_FragDepth = logDepth;
}

This guarantees correct depth resolution across long triangles, such as terrain patches or orbital rings.

Vertex Shader Approach

Modifying gl_FragDepth disables hardware Early-Z culling, which can impact performance in fragment-heavy scenes. An alternative is calculating the logarithmic depth in the vertex shader by adjusting the clip-space coordinate:

// Vertex Shader
uniform mat4 u_modelViewProjection;
const float C = 1.0;

void main() {
    vec4 clipPos = u_modelViewProjection * vec4(position, 1.0);
    
    // Scale clip-space z and w using the logarithmic factor
    clipPos.z = (2.0 * log(C * clipPos.w + 1.0) / log(C * u_farPlane + 1.0) - 1.0) * clipPos.w;
    gl_Position = clipPos;
}

Because modern graphics hardware linearly interpolates clip-space coordinates before depth testing, this vertex-only optimization can cause slight curvature or clipping artifacts on large, coarse triangles. Consequently, meshes must be sufficiently tessellated when using the vertex-only variant.

Architectural Trade-offs

Using logarithmic depth buffers requires managing specific graphics pipeline behaviors:

  1. Hardware Depth Clipping: Traditional OpenGL hardware clipping occurs against a linear homogenous clip volume. Severe depth warping can lead to near-plane clipping anomalies unless clip distances are correctly biased or depth clamping (GL_DEPTH_CLAMP) is enabled.
  2. Early-Z Performance: Writing to gl_FragDepth disables early fragment rejection optimizations. To mitigate fill-rate bottlenecks, developers often employ conservative depth output flags (layout (depth_greater) out float gl_FragDepth;) where hardware support is available, or use the vertex-stage formulation for dense geometry.
  3. Reversed-Z Complement: When combined with a 32-bit floating-point depth buffer (GL_DEPTH_COMPONENT32F) and a reversed depth setup (near plane at 1.0, far plane at 0.0), logarithmic mapping often becomes unnecessary for terrestrial scales. However, for true planetary scales where coordinate systems span billions of units, logarithmic depth remains the primary technique to maintain stability.

OpenGL Compute Shader Indirect Draw Synchronization

Generating draw parameters directly on the GPU using compute shaders requires explicit memory synchronization before executing indirect draw calls. Because OpenGL uses a weakly ordered, incoherent memory model for shader writes, you must use glMemoryBarrier with the GL_COMMAND_BARRIER_BIT flag to guarantee that writes from a compute shader are completely finished and visible to the GPU's indirect command processor before glDrawArraysIndirect or glDrawElementsIndirect is called. Failing to properly synchronize these operations leads to race conditions, rendering artifacts, or GPU crashes.

The Memory Incoherency Problem

Compute shaders write draw parameters to a buffer bound as a Shader Storage Buffer Object (SSBO). These writes are stored in GPU L1/L2 caches and are not automatically coherent with fixed-function pipeline stages.

The indirect drawing hardware operates outside the standard shader cache pipeline when reading execution parameters like instance counts, vertex offsets, and index counts from a GL_DRAW_INDIRECT_BUFFER. Without an explicit barrier, the GPU can issue the indirect draw command using stale, uninitialized, or partially written buffer data.

The Core Requirement: glMemoryBarrier

The primary mechanism to synchronize compute writes with indirect draws is the API call:

glMemoryBarrier(GL_COMMAND_BARRIER_BIT);

Calling glMemoryBarrier with GL_COMMAND_BARRIER_BIT instructs the driver to flush the necessary shader write caches and halt dependent command reads until all preceding shader stores to buffer objects have completed.

Barrier Placement

The barrier must be placed on the host timeline between the compute shader dispatch and the indirect draw invocation:

  1. Bind the buffer to GL_SHADER_STORAGE_BUFFER.
  2. Dispatch the compute shader (glDispatchCompute).
  3. Call glMemoryBarrier(GL_COMMAND_BARRIER_BIT).
  4. Bind the buffer to GL_DRAW_INDIRECT_BUFFER.
  5. Execute the draw call (glDrawArraysIndirect or glDrawElementsIndirect).

Binding the buffer target can occur before or after the barrier, but the barrier execution itself must happen after glDispatchCompute and before the draw command.

Synchronizing Accompanying Data

In GPU-driven rendering pipelines, a compute shader typically outputs more than just the indirect draw arguments. If the compute pass also performs frustum culling, generates instance matrices, or outputs index/vertex data, additional barrier bits must be combined using a bitwise OR operation.

  • GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT: Required if the compute shader writes per-instance or per-vertex data consumed by vertex attribute arrays.
  • GL_ELEMENT_ARRAY_BARRIER_BIT: Required if the compute shader writes or modifies index buffers used by glDrawElementsIndirect.
  • GL_SHADER_STORAGE_BARRIER_BIT: Required if the subsequent vertex or fragment shader reads the output buffer as an SSBO rather than a vertex attribute.

Example of a compound barrier:

glMemoryBarrier(GL_COMMAND_BARRIER_BIT | GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT);

Internal Shader Synchronization

Synchronization within the compute shader itself is handled separately:

  • If individual threads within a local workgroup coordinate their writes to the indirect buffer, you must use the GLSL built-in barrier() and memoryBarrierBuffer().
  • If each indirect draw command is written by a single thread independently with no cross-thread dependencies, intra-shader barriers are unnecessary, and only the host-level glMemoryBarrier is required.

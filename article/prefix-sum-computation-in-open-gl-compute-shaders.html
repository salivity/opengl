Prefix Sum Computation in OpenGL Compute Shaders

Prefix sum, commonly referred to as a parallel scan, is a fundamental algorithmic primitive that transforms an input array into an array of running totals. While trivial sequentially, adapting prefix sums to massively parallel hardware like graphics processing units (GPUs) requires rethinking data dependencies. This article explores the mathematical definition of inclusive and exclusive prefix sums, details parallel scan algorithms such as Hillis-Steele and Blelloch, and demonstrates how to adapt and implement them efficiently within an OpenGL compute shader architecture using shared memory, barriers, and multi-pass dispatches.

What is Prefix Sum Computation?

Given an ordered sequence of elements \([a_0, a_1, a_2, \dots, a_{n-1}]\) and an associative binary operator \(\oplus\) (typically addition), the prefix sum produces a sequence \([y_0, y_1, y_2, \dots, y_{n-1}]\).

Prefix sums fall into two categories:

  • Inclusive Scan: The \(k\)-th output element includes the \(k\)-th input element: \[y_k = a_0 \oplus a_1 \oplus \dots \oplus a_k\]
  • Exclusive Scan: The \(k\)-th output element includes all preceding elements except the current one, initialized with an identity element \(I\) (e.g., \(0\) for addition): \[y_k = I \oplus a_0 \oplus \dots \oplus a_{k-1} \quad (\text{with } y_0 = I)\]

Prefix sums serve as building blocks for numerous parallel algorithms, including stream compaction, radix sort, collision detection, and variable-length allocation on the GPU.

Adapting Prefix Sum to OpenGL Compute Shaders

A sequential prefix sum runs in \(O(N)\) time on a single CPU thread. In an OpenGL compute shader, sequential iteration fails to leverage thousands of available cores. Parallel adaptations rely on tree-based computation schemes, utilizing compute shader work-groups, local invocations, shared memory, and memory barriers.

1. Hardware Primitives in OpenGL

To map a scan to OpenGL, the algorithm must interact with the compute pipeline:

  • Shader Storage Buffer Objects (SSBOs): Provide global, read/write access to input and output arrays.
  • Shared Memory (shared keyword): Fast, on-chip scratchpad memory accessible by all invocations within a single work-group.
  • Barriers (barrier()): Synchronize execution across all invocations in a work-group to prevent race conditions during iterative steps.

2. Intra-Workgroup Algorithms

For array segments that fit inside a single work-group's shared memory, two primary algorithms are used:

  • Hillis-Steele (Step-Efficient): This approach computes the scan in \(\log_2(N)\) steps. In each step \(d\), invocation \(i\) adds the element at \(i - 2^d\) to its current value. Although simple and requiring fewer synchronization steps, it performs \(O(N \log N)\) total additions, making it work-inefficient for large datasets.
  • Blelloch (Work-Efficient): The Blelloch scan performs \(O(N)\) operations with \(2 \log_2(N)\) steps, split into two phases:
    1. Up-Sweep (Reduce): Builds a binary tree of partial sums in shared memory.
    2. Down-Sweep: Replaces the root with the identity element and traverses down the tree to construct the exclusive scan.

3. Single Work-Group Implementation Example

The following GLSL compute shader snippet illustrates a basic shared-memory exclusive scan (Blelloch) for an array of size \(N\) matching the work-group size:

#version 430
layout(local_size_x = 512) in;

layout(std430, binding = 0) readonly buffer InputBuffer {
    uint in_data[];
};
layout(std430, binding = 1) writeonly buffer OutputBuffer {
    uint out_data[];
};

shared uint temp[1024]; // Sized for 2 elements per invocation

void main() {
    uint thid = gl_LocalInvocationID.x;
    uint offset = 1;
    uint n = 1024;

    // Load data from global to shared memory
    temp[2 * thid]     = in_data[2 * thid];
    temp[2 * thid + 1] = in_data[2 * thid + 1];

    // Up-sweep (Reduce) phase
    for (uint d = n >> 1; d > 0; d >>= 1) {
        barrier();
        if (thid < d) {
            uint ai = offset * (2 * thid + 1) - 1;
            uint bi = offset * (2 * thid + 2) - 1;
            temp[bi] += temp[ai];
        }
        offset *= 2;
    }

    // Clear the last element for exclusive scan
    if (thid == 0) {
        temp[n - 1] = 0;
    }

    // Down-sweep phase
    for (uint d = 1; d < n; d *= 2) {
        offset >>= 1;
        barrier();
        if (thid < d) {
            uint ai = offset * (2 * thid + 1) - 1;
            uint bi = offset * (2 * thid + 2) - 1;
            uint t = temp[ai];
            temp[ai] = temp[bi];
            temp[bi] += t;
        }
    }
    barrier();

    // Write results back to global memory
    out_data[2 * thid]     = temp[2 * thid];
    out_data[2 * thid + 1] = temp[2 * thid + 1];
}

Scaling Beyond a Single Work-Group

OpenGL compute shaders do not provide global execution synchronization across independent work-groups. Processing arrays larger than the maximum work-group shared memory limit requires a hierarchical, multi-pass dispatch approach:

  1. Block Scan: The input array is divided into blocks corresponding to individual work-groups. Each work-group calculates the prefix sum of its block locally and writes the total sum of its block into an auxiliary buffer.
  2. Scan Block Sums: The auxiliary buffer of block totals is scanned. If the number of blocks exceeds a single work-group, this step is applied recursively; otherwise, it runs in a single work-group dispatch.
  3. Uniform Addition: A final compute shader dispatch reads the scanned block totals and adds each block's base offset to every element in the corresponding block.

Optimizations and Hardware Considerations

  • Shared Memory Bank Conflicts: Sequential access patterns across threads in shared memory can lead to hardware bank conflicts. Padding the shared array indices prevents simultaneous access to the same memory banks.
  • Subgroup Operations: Modern OpenGL extensions (such as GL_KHR_shader_subgroup_arithmetic) allow operations directly across hardware warps/wavefronts without using shared memory, enabling subgroup-level scans (subgroupInclusiveAdd) that drastically reduce latency in the first reduction stages.

How textureGather Works in Modern OpenGL

Modern OpenGL provides the textureGather function to retrieve the four adjacent texels that would normally participate in bilinear filtering in a single operation, returning their raw values directly to the shader rather than blending them. By tapping directly into the hardware architecture of the GPU's Texture Mapping Units (TMUs), this instruction significantly reduces texture fetch overhead. This article explains the underlying hardware mechanisms, texel mapping conventions, and use cases that make textureGather an essential tool for high-performance rendering.

The Mechanism of Bilinear Footprints

Under standard texture sampling using functions like texture(), a 2D sampler configured for linear filtering determines the floating-point coordinate within the texture, locates the \(2 \times 2\) bounding box of neighboring texels, and performs a weighted average based on fractional offsets:

\[\text{Final Color} = \sum_{k=1}^{4} w_k \cdot \text{Texel}_k\]

To calculate this blend, the GPU hardware must already load all four adjacent texels into memory registers inside the TMU.

textureGather exploits this existing hardware path by bypassing the weighting and summation phase. Instead of returning a blended color vector (vec4), it extracts a single color channel from all four adjacent texels and packs them into a single vec4, returning the unblended values directly to the fragment shader in a single instruction.

Texel Component Ordering

Because a standard vector register contains four components (x, y, z, w), textureGather queries a specific single channel (red, green, blue, or alpha) across the four texels. By default, the red channel (component index 0) is retrieved if none is explicitly specified.

Given a base texel coordinate \((i, j)\), the four retrieved texels are arranged in counter-clockwise order within the output vector according to the OpenGL specification:

  • .x: Texel \((i, j + 1)\) (Top-Left)
  • .y: Texel \((i + 1, j + 1)\) (Top-Right)
  • .z: Texel \((i + 1, j)\) (Bottom-Right)
  • .w: Texel \((i, j)\) (Bottom-Left)

This deterministic mapping allows developers to reconstruct the local \(2 \times 2\) neighborhood with precise spatial awareness.

Hardware-Level Execution

Modern GPU architectures process texture sampling requests using dedicated memory caches (L1 texture caches) and TMUs. Normally, issuing four separate point-filtered fetches (texelFetch) requires four distinct load operations, instruction dispatches, and address computations.

With textureGather, the GPU issues a single memory address calculation. The TMU fetches the cache line containing the quad, routes the target channel from each of the four texels across the internal crossbar, and commits the packed 128-bit vector directly to the general-purpose registers (VGPRs). This yields a fourfold reduction in texture instruction overhead and maximizes cache line reuse, avoiding redundant memory requests.

Practical Applications

  1. Percentage-Closer Filtering (PCF) in Shadow Mapping: Instead of sampling a depth map four times to calculate shadow softness, a single textureGather call retrieves all four depth values at once. The comparison with the current fragment's depth can then be vectorized across all four components simultaneously using SIMD operations.
  2. Custom Reconstruction Filters: Algorithms like bicubic, Catmull-Rom, or Lanczos filtering require sampling a larger footprint (such as \(4 \times 4\)). Using standard fetches requires 16 separate samples; using textureGather, the entire footprint is captured using only four instructions.
  3. Screen-Space Ambient Occlusion (SSAO) and Edge Detection: Gathering neighboring normal or linear depth components reduces texture pipeline stalls when calculating high-frequency spatial gradients.

OpenGL Texture Format Compatibility Guarantees

The OpenGL specification provides strict rules and baseline requirements for texture format compatibility to ensure consistent behavior across different hardware vendors and operating systems. While early versions of OpenGL left format selection largely to driver discretion, modern OpenGL versions (OpenGL 3.0 and later, as well as OpenGL ES 3.0 and later) mandate specific internal formats, well-defined conversion rules between client data and GPU storage, and explicit compatibility classes for advanced features like texture views. Understanding these guarantees allows developers to write portable, predictable, and performant graphics applications without relying on vendor-specific behavior.

Mandated Sized Internal Formats

Prior to OpenGL 3.0, developers often supplied unsized internal formats (such as GL_RGB or GL_RGBA), allowing drivers to choose the underlying storage precision. In modern core OpenGL, the specification mandates support for a comprehensive set of explicitly sized internal formats. Conformance tests require that any certified driver accurately allocates and supports the following format categories:

  • Standard Color Formats: Fixed-point normalized formats such as GL_R8, GL_RG8, GL_RGB8, GL_RGBA8, and their 16-bit variants (GL_RGBA16). Signed normalized variants (e.g., GL_RGBA8_SNORM) are also guaranteed.
  • Floating-Point Formats: 16-bit and 32-bit floating-point types, including GL_R16F, GL_RG32F, GL_RGBA32F, and packed types like GL_R11F_G11F_B10F.
  • Integer Formats: Unsigned and signed pure integer formats (e.g., GL_RGBA8UI, GL_RGBA32I), which do not normalize values and require integer samplers in shaders.
  • Depth and Stencil Formats: GL_DEPTH_COMPONENT16, GL_DEPTH_COMPONENT24, GL_DEPTH_COMPONENT32F, and combined formats like GL_DEPTH24_STENCIL8 and GL_DEPTH32F_STENCIL8.
  • sRGB Formats: Formats providing automatic hardware linear-to-sRGB and sRGB-to-linear conversions, notably GL_SRGB8 and GL_SRGB8_ALPHA8.

Implementations are forbidden from substituting a mandated format with one of lower precision.

Client Upload and Download Compatibility

When transferring data between host memory and textures via functions like glTexImage2D or glTexSubImage2D, developers specify a client data format (e.g., GL_RGBA) and type (e.g., GL_UNSIGNED_BYTE).

The OpenGL specification guarantees that the implementation will automatically perform any required conversions between the client-specified representation and the internal texture storage format. For example, uploading unsigned byte data to a floating-point texture or uploading float data to a normalized integer texture is explicitly valid. However, integer internal formats (e.g., GL_RGBA32UI) must be matched with integer pixel formats (e.g., GL_RGBA_INTEGER) to avoid invalid operation errors.

To query the driver's preferred and most efficient format-type pairing for a specific texture format, the specification provides queries via glGetInternalformativ:

GLint preferredType, preferredFormat;
glGetInternalformativ(GL_TEXTURE_2D, GL_RGBA8, GL_TEXTURE_IMAGE_TYPE, 1, &preferredType);
glGetInternalformativ(GL_TEXTURE_2D, GL_RGBA8, GL_TEXTURE_IMAGE_FORMAT, 1, &preferredFormat);

Framebuffer Attachment and Renderability Guarantees

Not all valid texture formats are guaranteed to be renderable. The OpenGL specification explicitly distinguishes between texture-filterable formats and renderable formats:

  1. Color-Renderable: Mandated sized formats such as GL_RGBA8, GL_RGBA16F, and GL_RGBA32I can be attached to a Framebuffer Object (FBO) as color buffers. If an implementation supports an internal format marked as color-renderable in the specification tables, it must result in a GL_FRAMEBUFFER_COMPLETE state when attached.
  2. Depth/Stencil-Renderable: Formats designated as depth/stencil can be bound to the respective FBO attachment points.
  3. Filtering Capabilities: Formats like GL_RGBA32F are guaranteed to be usable as textures, but full linear filtering support for 32-bit floating-point textures is not universally mandated across all profiles without specific extensions or core version requirements.

If an unsupported or non-renderable format is attached to an FBO, the specification requires glCheckFramebufferStatus to return GL_FRAMEBUFFER_INCOMPLETE_ATTACHMENT or GL_FRAMEBUFFER_UNSUPPORTED.

Texture View Compatibility Classes

Introduced in OpenGL 4.3 (and via the ARB_texture_view extension), texture views permit an existing texture's data store to be reinterpreted using a different target or internal format without copying memory.

The specification strictly dictates compatibility for texture views based on format classes. Two formats are compatible for use in a texture view if and only if they belong to the same size class and share the same bit layout per component or texel.

Key compatibility classes include:

  • 128-Bit Class: GL_RGBA32F, GL_RGBA32UI, GL_RGBA32I
  • 64-Bit Class: GL_RGBA16F, GL_RGBA16UI, GL_RGBA16I, GL_RGBA16, GL_RGBA16_SNORM, GL_RG32F, GL_RG32UI, GL_RG32I
  • 32-Bit Class: GL_RGBA8, GL_RGBA8UI, GL_RGBA8I, GL_RGBA8_SNORM, GL_SRGB8_ALPHA8, GL_RGB10_A2, GL_R11F_G11F_B10F, GL_RG16F, GL_RG16, GL_R32F, GL_R32UI, GL_R32I
  • 16-Bit Class: GL_RG8, GL_RG8I, GL_RG8UI, GL_R16F, GL_R16I, GL_R16UI, GL_R16
  • 8-Bit Class: GL_R8, GL_R8I, GL_R8UI, GL_R8_SNORM

Attempting to create a texture view using formats from different compatibility classes generates a GL_INVALID_OPERATION error.

Compressed Texture Guarantees

Texture compression guarantees vary by version:

  • OpenGL 4.3 and OpenGL ES 3.0+: ETC2/EAC formats (e.g., GL_COMPRESSED_RGB8_ETC2, GL_COMPRESSED_RGBA8_ETC2_EAC) are core requirements. All compliant drivers must decode these formats natively in hardware or via guaranteed runtime decompression.
  • Desktop OpenGL (Legacy and Pre-4.3): S3TC (DXT1/DXT5, exposed via GL_EXT_texture_compression_s3tc) was technically an extension due to patent restrictions, though nearly universally implemented. Modern implementations support modern formats like BPTC (GL_COMPRESSED_RGBA_BPTC_UNORM) natively starting in OpenGL 4.2.

The specification guarantees that querying GL_NUM_COMPRESSED_TEXTURE_FORMATS and GL_COMPRESSED_TEXTURE_FORMATS will yield all formats that can be accepted without generating an error during texture definition.

Image Load/Store Compatibility

For compute shaders and arbitrary read/write access via glBindImageTexture, the OpenGL specification enforces that the format specified in the API call must match the memory qualifier format declared in the GLSL shader (e.g., layout(rgba8) uniform image2D img;). While formats with identical bit layouts can be bound under relaxed conditions if the driver supports format qualifiers, strict type compatibility matches the rules laid out in the texture view specification to prevent undefined hardware behavior during memory reads and writes.

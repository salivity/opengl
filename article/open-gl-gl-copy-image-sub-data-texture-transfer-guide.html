OpenGL glCopyImageSubData Texture Transfer Guide

The glCopyImageSubData function in OpenGL provides an efficient mechanism for directly copying raw texel data between textures or renderbuffers entirely on the GPU. By eliminating the overhead of binding images to framebuffers or routing data through host CPU memory, it enables high-throughput data transfers across resources. This article outlines the primary function of the API, its operational mechanics, format compatibility rules, and its advantages over traditional texture copying methods.

Core Function of glCopyImageSubData

The primary function of glCopyImageSubData is to perform a direct, memory-to-memory block copy of texels from a defined region of a source image to a destination image. Introduced as a core feature in OpenGL 4.3 (and available in OpenGL 4.2 via the ARB_copy_image extension), this API treats textures and renderbuffers as raw memory allocations rather than render targets, bypassing the standard rendering pipeline entirely.

Key Capabilities and Mechanics

When transferring data between textures, glCopyImageSubData provides several distinct operational features:

  • Direct GPU Transfer: The copy operation executes entirely within GPU memory using dedicated copy engines (DMA transfers), preventing costly CPU-GPU synchronization stalls and avoiding CPU round-trips.
  • No Context Binding Required: Traditional methods require binding textures to Framebuffer Objects (FBOs) or texture units. glCopyImageSubData operates directly on texture object handles (GLuint), which reduces OpenGL state changes and driver overhead.
  • Cross-Target Transfers: The function can copy data between differing texture types, provided dimensional compatibility is maintained. For example, you can copy a slice of a 2D texture array into a standard 2D texture, or transfer data between a renderbuffer and a texture.
  • 3D Region Definition: It supports copying arbitrary sub-regions using offset coordinates (\(x, y, z\)) and dimensions (width, height, depth) for both the source and destination at specified mipmap levels.

Format Compatibility and Bit-for-Bit Copying

A critical aspect of glCopyImageSubData is that it does not perform format conversion, filtering, or scaling. It executes a bit-for-bit copy. Because of this, the source and destination internal formats must be compatible:

  1. Matching Texel Sizes: The internal formats must belong to the same format class, meaning they share the same bit-depth per texel. For instance, copying between GL_RGBA8 and GL_R32UI is permitted because both represent 32 bits per texel.
  2. Compressed Formats: Block-compressed textures (such as BCn or ASTC) can also be transferred, provided the block dimensions and overall byte sizes match, and the defined regions align with the compression block boundaries.

Advantages Over Alternative Methods

Prior to glCopyImageSubData, transferring data between textures required either glBlitFramebuffer or reading back data with glGetTexImage and re-uploading via glTexSubImage2D.

Compared to glBlitFramebuffer, glCopyImageSubData does not require configuring FBO attachments, does not alter the viewport or scissor states, and avoids the overhead of fragment operations. While glBlitFramebuffer is necessary when linear filtering, stretching, or format conversions are needed, glCopyImageSubData is the optimal choice for pure, identical-size data replication across GPU resources.

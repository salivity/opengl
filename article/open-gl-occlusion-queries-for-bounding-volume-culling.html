OpenGL Occlusion Queries for Bounding Volume Culling

OpenGL occlusion queries provide a hardware-accelerated mechanism to determine whether rendered geometry is visible on screen or occluded by other objects. By drawing lightweight bounding volumes—such as axis-aligned bounding boxes (AABB) or bounding spheres—inside an occlusion query, developers can test for visibility without rendering complex meshes. The CPU reads back these visibility results to cull fully occluded objects before issuing expensive draw calls, state changes, and shader computations. This article explains how OpenGL occlusion queries function, how they integrate into bounding volume culling pipelines, and how to manage CPU-GPU synchronization issues.

Understanding OpenGL Occlusion Queries

An occlusion query is an asynchronous GPU operation that counts the number of fragments or samples that pass depth and stencil tests during rasterization.

To use an occlusion query in OpenGL:

  1. Generate a query object using glGenQueries.
  2. Delimit the target geometry using glBeginQuery and glEndQuery.
  3. Retrieve the visibility outcome using glGetQueryObjectuiv.

OpenGL provides different query targets depending on the required precision:

  • GL_SAMPLES_PASSED: Returns the exact number of samples that passed the depth/stencil test.
  • GL_ANY_SAMPLES_PASSED: Returns a boolean-like result indicating whether at least one sample was visible.
  • GL_ANY_SAMPLES_PASSED_CONSERVATIVE: Similar to GL_ANY_SAMPLES_PASSED, but allows the GPU driver to use faster, less precise hardware algorithms that favor performance over exact fragment accounting.

For culling purposes, GL_ANY_SAMPLES_PASSED or its conservative counterpart is preferred because determining simple visibility does not require an exact sample count.

The Concept of Bounding Volume Culling

Rendering complex 3D meshes with high vertex counts and intensive fragment shaders wastes GPU resources if those meshes are completely hidden behind walls, terrain, or other large occluders.

A bounding volume is a geometrically simple primitive (such as a box or sphere) that completely encloses a complex mesh. Because the bounding volume encompasses the entire object:

  • If the bounding volume is completely occluded, the mesh inside is guaranteed to be occluded.
  • If any part of the bounding volume is visible, the mesh may be visible and must be rendered.

Testing the visibility of a simple 12-triangle bounding cube is significantly cheaper than rendering a high-polygon character or environment asset.

The Implementation Pipeline

Integrating occlusion queries with CPU-side bounding volume culling requires a structured multi-pass rendering process:

1. Render Major Occluders

Render large, opaque scene geometry (such as terrain, buildings, or large structures) directly to the depth buffer. This establishes the initial depth representation against which subsequent objects will be tested.

2. Disable Color and Depth Writes

Before testing bounding volumes, disable writes to the color buffer and depth buffer:

glColorMask(GL_FALSE, GL_FALSE, GL_FALSE, GL_FALSE);
glDepthMask(GL_FALSE);

The bounding volumes should only test against existing depth values without altering the screen or the depth buffer.

3. Issue Bounding Volume Queries

Iterate through potential objects and render their bounding volumes within query blocks:

glBeginQuery(GL_ANY_SAMPLES_PASSED, queryIDs[i]);
RenderBoundingVolume(object[i]);
glEndQuery(GL_ANY_SAMPLES_PASSED);

4. Restore Write Masks

Re-enable color and depth writes:

glColorMask(GL_TRUE, GL_TRUE, GL_TRUE, GL_TRUE);
glDepthMask(GL_TRUE);

5. Evaluate Results and Cull on the CPU

The CPU fetches the result of each query object:

GLuint visible = GL_FALSE;
glGetQueryObjectuiv(queryIDs[i], GL_QUERY_RESULT, &visible);

if (visible) {
    RenderComplexMesh(object[i]);
}

If visible returns GL_FALSE, the CPU skips the draw calls and state bindings for that object entirely.

Handling the CPU-GPU Synchronization Bottleneck

The primary challenge of CPU-side culling via occlusion queries is hardware synchronization latency.

When the CPU calls glGetQueryObjectuiv(..., GL_QUERY_RESULT, ...), it requests data generated by the GPU pipeline. If the GPU has not finished rendering the bounding volume, the CPU must stall (idle) until the query completes, which can degrade overall frame rates.

To mitigate pipeline stalls:

  • Asynchronous Polling: Query the availability of the result first using GL_QUERY_RESULT_AVAILABLE. If the result is not yet available, the CPU can continue processing other game logic instead of idling.
  • Temporal Coherence (Frame Delay): Use the query results from frame \(N-1\) to decide whether to render the object in frame \(N\), while issuing a new query in the background. Because camera movements and scene changes between adjacent frames are usually minor, this approach minimizes pipeline stalls at the cost of a single-frame visibility delay.
  • Hierarchical Culling: Organize bounding volumes into an octree or bounding volume hierarchy (BVH). Query the parent node's volume first; if the parent node is occluded, all of its child objects are automatically culled, drastically reducing the total number of queries submitted to the GPU.

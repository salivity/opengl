OpenGL Bindless Textures and 64-Bit Handles

Bindless texture technology radically transforms resource management in modern OpenGL by converting traditional texture objects into direct 64-bit integer handles, bypassing standard binding slots and CPU overhead. This article explains how the ARB_bindless_texture extension extracts internal GPU memory addresses and descriptors, makes them resident, and allows shaders to access an arbitrary number of textures directly through lightweight uniform or buffer data.

The Limitations of Traditional Texture Binding

In standard OpenGL, managing textures requires an indirect state-machine approach. Textures must be bound to specific context slots using glActiveTexture and glBindTexture. During a draw call, the graphics driver must validate the state of each bound unit, translate API texture IDs into device-level addresses, and map them to physical shader registers.

This model introduces significant CPU overhead. Furthermore, hardware imposes a strict limit on the number of simultaneous texture units available in a single shader stage, typically capping concurrent access to 16, 32, or 96 textures.

Generating the 64-Bit Texture Handle

The ARB_bindless_texture extension circumvents API state tracking by converting a texture into a 64-bit unsigned integer (GLuint64). This conversion is handled primarily through the API function:

GLuint64 handle = glGetTextureHandleARB(textureID);

When this function is called, the graphics driver resolves the texture's state—including its dimensions, format, mipmap hierarchy, filtering parameters, and physical virtual memory address (VRAM pointer). The driver packs this metadata, or an index into an internal hardware descriptor table, into a single 64-bit scalar value.

If a texture requires a non-standard sampler state, developers can alternatively invoke glGetTextureSamplerHandleARB(textureID, samplerID) to combine the underlying texture storage with a specific hardware sampler state into a unique 64-bit handle. Once generated, this handle is immutable; the texture's format, dimensions, and mip levels can no longer be modified.

Ensuring Memory Residency

Before a shader can dereference a raw 64-bit handle, the underlying memory must be locked into GPU virtual address space to prevent paging or eviction. This is accomplished via residency management:

glMakeTextureHandleResidentARB(handle);

Calling this function instructs the driver’s memory manager that the physical memory pages backing the texture must remain mapped and accessible to the GPU. The texture remains resident until explicitly released with glMakeTextureHandleNonResidentARB(handle). This shifts memory lifecycle management directly onto the application, removing per-draw-call validation overhead on the CPU.

Consuming Handles Inside Shaders

Because the handle is simply a 64-bit integer, it does not occupy a texture binding slot. It can be passed to the GPU like any standard primitive data type. Applications can store thousands of handles inside Uniform Buffer Objects (UBOs), Shader Storage Buffer Objects (SSBOs), or even vertex attributes.

In GLSL, the extension allows casting or implicitly interpreting the 64-bit handle as a sampler type:

#version 450
#extension GL_ARB_bindless_texture : require

layout(std430, binding = 0) buffer TextureBuffer {
    sampler2D materials[];
};

flat in int materialIndex;
out vec4 fragColor;

void main() {
    sampler2D activeSampler = materials[materialIndex];
    fragColor = texture(activeSampler, vec2(0.5, 0.5));
}

At the hardware execution level, the GPU treats the 64-bit value as a direct pointer or hardware-level descriptor offset. When a sampling instruction is executed, the GPU hardware fetches the texture descriptor directly from memory rather than querying context state registers, enabling vast material variations within a single draw call.

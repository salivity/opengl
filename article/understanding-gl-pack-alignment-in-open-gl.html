Understanding GL_PACK_ALIGNMENT in OpenGL

This article explains the significance of the GL_PACK_ALIGNMENT parameter in OpenGL, focusing on how it governs byte alignment during pixel readback operations such as glReadPixels. You will learn how the parameter dictates row padding when data travels from the GPU to host memory, the visual artifacts and memory corruption that occur when it is misconfigured, and how to correctly set it to prevent common image download bugs.

When downloading pixel data from the GPU into client application memory, OpenGL uses pixel storage modes to determine how individual bytes are arranged in destination buffers. The parameter GL_PACK_ALIGNMENT, configured using glPixelStorei, defines the byte boundary to which the start of each pixel row must be aligned.

Pack vs. Unpack

OpenGL distinguishes between sending data to the GPU and reading it back:

  • GL_UNPACK_* parameters control how OpenGL reads (unpacks) pixel data from client memory when uploading to textures via functions like glTexImage2D.
  • GL_PACK_* parameters control how OpenGL writes (packs) pixel data into client memory when retrieving buffers through functions like glReadPixels or glGetTexImage.

The Default Value and How Padding Works

By default, OpenGL sets GL_PACK_ALIGNMENT to 4. This means OpenGL requires the beginning of each row of pixels in destination memory to start on a memory address that is a multiple of 4 bytes.

If the byte length of a single row is not naturally divisible by 4, OpenGL automatically inserts padding bytes at the end of each row before writing the next one.

  • Formula for Row Stride: If an image has width \(W\) and \(B\) bytes per pixel, the raw row size is \(W \times B\). If GL_PACK_ALIGNMENT is \(A\) (where \(A \in \{1, 2, 4, 8\}\)), OpenGL rounds the row length up to the nearest multiple of \(A\): \[\text{Row Stride} = \left\lfloor \frac{W \times B + A - 1}{A} \right\rfloor \times A\]

The Skewing Bug

A common bug occurs when working with formats where pixels do not naturally align to 4 bytes, such as 3-byte RGB (GL_RGB, GL_UNSIGNED_BYTE) or 1-byte grayscale (GL_RED, GL_UNSIGNED_BYTE).

Consider an RGB image with a width of 5 pixels:

  • Raw row size: \(5 \text{ pixels} \times 3 \text{ bytes} = 15 \text{ bytes}\).
  • Because 15 is not divisible by 4, a default GL_PACK_ALIGNMENT of 4 pads the row to 16 bytes.
  • When executing glReadPixels, OpenGL writes 16 bytes per row instead of 15.

If the receiving buffer was allocated assuming tightly packed data (\(5 \times 3 \times \text{height}\)), two problems occur:

  1. Visual Skew: Each successive row starts one byte later than expected, causing the final reconstructed image to appear diagonally tilted or sheared with incorrect colors.
  2. Buffer Overflow: The extra padding byte per row causes the total written data to exceed the allocated buffer size on the final rows, potentially causing undefined behavior or segmentation faults.

Correcting the Alignment

To prevent automatic padding and download rows as tightly packed bytes, set GL_PACK_ALIGNMENT to 1 before reading pixels:

glPixelStorei(GL_PACK_ALIGNMENT, 1);
glReadPixels(0, 0, width, height, GL_RGB, GL_UNSIGNED_BYTE, buffer);

Valid values for the alignment parameter are 1, 2, 4, and 8:

  • 1: Byte-aligned; no padding is added (ideal for arbitrary-dimension RGB or single-channel data).
  • 2: Rows aligned to 16-bit boundaries.
  • 4: Word-aligned (default; ideal for 32-bit RGBA formats).
  • 8: Double-word aligned (often used for 64-bit data structures or SIMD architectures).

Performance Considerations

Hardware architectures and memory controllers transfer data more efficiently when memory addresses align to 4-byte or 8-byte boundaries. While setting GL_PACK_ALIGNMENT to 1 ensures predictable data structures for file formats like PNG or JPEG, keeping higher alignments (such as 4 with GL_RGBA) maximizes memory bandwidth performance during large transfers.

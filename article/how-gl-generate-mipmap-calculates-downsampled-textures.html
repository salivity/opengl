How glGenerateMipmap Calculates Downsampled Textures

This article examines how OpenGL's glGenerateMipmap function computes the downsampled mipmap chain for textures directly on the graphics processing unit (GPU). It details the mathematical dimension halving, the spatial filtering algorithms used by GPU drivers, hardware execution pipelines (such as blitting and compute shaders), and critical considerations such as sRGB color-space conversions and non-power-of-two dimensions.

The Mipmap Pyramid and Dimension Reduction

When glGenerateMipmap is called, the GPU builds a complete pyramid of progressively lower-resolution images, starting from the defined base level (typically level 0) down to a \(1 \times 1\) texel image.

For any given level \(k\), the dimensions of the next mipmap level \(k+1\) are derived by halving the width, height, and depth, rounding down to the nearest integer, with a minimum clamp of 1:

\[\text{width}_{k+1} = \max(1, \lfloor \text{width}_k / 2 \rfloor)\] \[\text{height}_{k+1} = \max(1, \lfloor \text{height}_k / 2 \rfloor)\] \[\text{depth}_{k+1} = \max(1, \lfloor \text{depth}_k / 2 \rfloor)\]

This process continues recursively until all dimensions reach 1.

Downsampling Filter Kernels

The OpenGL specification allows the exact downsampling algorithm to be implementation-dependent, but almost all modern GPU hardware and drivers employ a box filter (area averaging) due to its high efficiency in hardware.

  • 2D Textures: A \(2 \times 2\) texel footprint from level \(k\) is averaged to compute one texel in level \(k+1\). Each of the four texels contributes an equal 25% weight to the destination texel: \[\text{Texel}_{k+1}(x, y) = \frac{1}{4} \sum_{i=0}^{1} \sum_{j=0}^{1} \text{Texel}_k(2x + i, 2y + j)\]
  • 3D Textures: A \(2 \times 2 \times 2\) block of 8 texels is averaged, each contributing 12.5% weight.
  • 1D Textures: Adjacent pairs of texels are averaged with equal 50% weights.

Handling Odd and Non-Power-of-Two (NPOT) Dimensions

When a dimension is odd, standard \(2 \times 2\) averaging leaves an uneven number of texels. Depending on the driver and hardware:

  1. The kernel may adjust coverage weights proportionally so border texels do not distort the average.
  2. The GPU may utilize hardware texture samplers using normalized coordinates with bilinear filtering, automatically sampling at the exact center between adjacent texels to let hardware linear interpolation approximate the box average.

GPU Execution Mechanisms

Rather than performing these operations on the CPU, glGenerateMipmap executes entirely on the GPU via one of several internal driver pathways:

  1. Hardware Blit / Rasterization Passes: The driver binds level \(k+1\) as a framebuffer attachment (or an internal render target) and renders a screen-aligned quad, sampling from level \(k\) using hardware bilinear filtering. Because hardware bilinear units can fetch and blend four texels in a single cycle, this method executes extremely fast.
  2. Compute Shaders: Modern drivers frequently implement glGenerateMipmap via internal compute shaders. A compute workgroup reads a tile of texels from level \(k\) into shared memory (LDS/Threadgroup memory), performs local reductions, and writes the downsampled outputs to level \(k+1\) (and often \(k+2\) within the same pass) using image stores.
  3. Dedicated Copy/Media Engines: Certain architectures route sub-resource downsampling to dedicated 2D hardware copy engines equipped with fixed-function scaling units.

Color Space and sRGB Correctness

Downsampling in a non-linear color space causes perceptual darkening and incorrect contrast. When glGenerateMipmap is called on an sRGB-formatted texture (such as GL_SRGB8 or GL_SRGB8_ALPHA8):

  1. The GPU reads non-linear sRGB texels and hardware-converts them to linear floating-point values via the sRGB transfer function.
  2. The box filter calculates the mathematical mean in linear space.
  3. The resulting linear average is converted back into non-linear sRGB space before being written to level \(k+1\).

If a standard non-sRGB texture format (such as GL_RGBA8) is used for gamma-encoded color data, the GPU blindly averages the gamma values directly, causing perceptual loss of brightness in distant mip levels.

Precision and Filter Quality Limitations

Because glGenerateMipmap prioritizes generation speed over advanced signal processing:

  • It does not implement wide-support windowed sinc filters (such as Lanczos or Kaiser filters), which can lead to slight aliasing or high-frequency loss on high-contrast textures.
  • Intermediate results are generally stored at the format's native precision (e.g., 8-bit per channel), which can cause rounding errors across deep mip chains.

For offline asset pipelines or scenarios demanding high-fidelity anti-aliasing without energy loss, developers generate mipmaps manually using custom compute shaders or CPU-based filtering algorithms prior to uploading the data to OpenGL.

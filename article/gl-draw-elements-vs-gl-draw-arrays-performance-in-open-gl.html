glDrawElements vs glDrawArrays Performance in OpenGL

In OpenGL, geometry can be submitted to the GPU using flat arrays with glDrawArrays or indexed arrays with glDrawElements. This article compares the performance characteristics of both approaches, examining memory bandwidth, vertex cache utilization, index-fetch overhead, and real-world scenarios to help you determine the optimal rendering strategy for your graphics pipeline.

Memory Footprint and Bus Bandwidth

The primary architectural difference lies in how vertex data is stored and transferred. With glDrawArrays, vertices must be stored sequentially for every primitive. In a standard triangle mesh, adjacent triangles share edges and vertices; flat arrays force you to duplicate this data. For example, a simple cube requires 36 vertices (6 faces × 2 triangles × 3 vertices) when drawn flat, compared to 8 unique vertices and 36 indices when indexed.

Because modern vertex formats often contain positions, normals, tangents, and multiple texture coordinates—frequently exceeding 32 to 64 bytes per vertex—duplicating vertices severely inflates buffer sizes. glDrawElements introduces an index buffer containing lightweight integers (typically 16-bit GL_UNSIGNED_SHORT or 32-bit GL_UNSIGNED_INT). Storing small index values consumes substantially less VRAM and reduces memory bandwidth pressure during transfers from system memory to the GPU.

Post-Transform Vertex Cache

The most critical performance advantage of glDrawElements is its interaction with the GPU’s Post-Transform Vertex Cache (often referred to as the Post-Transform Cache or Parameter Cache).

When a GPU processes geometry via glDrawElements:

  1. It reads the index of the vertex.
  2. It checks a small hardware FIFO or LRU cache to see if that specific index was recently processed by the vertex shader.
  3. If a cache hit occurs, the vertex shader stage is skipped entirely, and the cached transformed attributes are passed directly to primitive assembly and rasterization.
  4. If a cache miss occurs, the vertex shader executes, and the result is stored in the cache.

With glDrawArrays, the GPU evaluates each vertex independently because it cannot safely assume that two identical vertex attribute sets represent the same logical point. Consequently, every vertex shader invocation runs unconditionally. In typical connected meshes with an average valence of 6 triangles per vertex, an optimized index buffer can reduce vertex shader invocations by a factor of two or three.

Index Fetch Overhead and Indirection

While glDrawElements is generally superior for complex geometry, it introduces an extra level of indirection. The GPU must fetch the index from the Element Array Buffer before it can address and fetch the corresponding vertex attributes.

This indirection cost becomes measurable when vertices cannot be shared:

  • Unique Vertex Attributes: When rendering flat-shaded low-poly meshes where each face has distinct surface normals, or models with separate texture coordinates at every boundary seam, vertices cannot be shared across adjacent triangles.
  • Point Clouds and Line Strips: Rendering independent points or non-indexed line segments yields no index reuse.
  • Procedural Billboards / Particles: When geometry is generated procedurally in shaders or through instancing without shared corner data.

If vertex sharing does not exist, using glDrawElements requires additional memory reads for the index buffer without providing any post-transform cache hits, causing glDrawArrays to be faster and simpler.

Optimizing for glDrawElements

To maximize the performance benefits of indexed rendering, index order should not be arbitrary. Mesh processing tools (such as Tom Forsyth’s Linear-Speed Vertex Cache Optimization algorithm or NV-TriStrip) reorder indices to maximize spatial locality. Reordering ensures that triangles sharing vertices are processed closely together in time, maximizing post-transform cache hit rates and minimizing pipeline stalls.

Summary of Usage

  • Use glDrawElements for standard 3D static and rigged meshes, terrain meshes, and any connected geometry where vertices are shared among multiple primitives.
  • Use glDrawArrays for non-indexed primitives such as particle point clouds, full-screen quads, UI elements with entirely unique per-vertex data, and data streams generated dynamically on the CPU where index calculation adds unnecessary overhead.
